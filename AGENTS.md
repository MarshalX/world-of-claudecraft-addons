# AGENTS.md

Working instructions for this repository. `CLAUDE.md` points here; this file is the single source of truth.

## What this is

A userscript addon platform for the browser game World of ClaudeCraft, plus the official addon marketplace. It is **fully external to the game**: no game source is modified and no build is forked.

Tampermonkey and Violentmonkey are first-class. Greasemonkey 4 is best-effort: it has no value-change listener, so cross-tab sync there runs over a BroadcastChannel fallback.

The loader has two halves in different JavaScript realms. The **host** runs in the userscript sandbox and owns GM storage, marketplace fetching, and the registry. The **runtime** is injected into the page realm and owns `window.__game`, the WebSocket hook, DOM, keybinds, audio, and the addon API. They talk over a Comlink-wrapped `MessageChannel`, and only storage, addon source, and registry state cross that boundary.

## Setup

```sh
corepack enable        # pins pnpm from package.json packageManager
pnpm install
```

Node 24 (`.nvmrc`). The tools import `.ts` modules directly and rely on Node's built-in type stripping, which is why every relative import carries an explicit `.ts` extension.

**Formatting is Biome, not Prettier.** Run `pnpm fix` rather than fixing style by hand. Config is `biome.json`: 2-space, `lineWidth` 100, single quotes, semicolons, trailing commas.

`pnpm fix` takes paths, and it has to: the script used to end in a literal `.`, so an argument was APPENDED to a whole-tree run rather than narrowing it, and `pnpm fix one-file.ts` silently rewrote all 501. Biome with no path defaults to the tree anyway, so dropping the `.` made the bare form identical and the argument form actually scope. It matters whenever more than one thing is editing the tree at once, where a whole-tree write can land on a file something else is halfway through saving. `pnpm lint` has always scoped, since it goes through `tools/lint.mjs`.

A bare `pnpm index` stamps `generated` with the current time, so it produces a one-line diff even when no addon changed. That is expected; CI stamps from the commit instead, so re-running on the same commit is byte-identical.

## Lint and type strictness

**Read [STYLE.md](STYLE.md) before writing a module.** It is the list of rules that actually fire in this repo, with the idiom that satisfies each, plus the two places Biome and TypeScript want opposite things. Writing rule-aware code costs a few seconds; discovering the same violations at the end of a change costs a restructuring pass, because most of these rules are asking for a real split rather than a formatting fix.

The linter runs Biome's **`preset: "all"`**, every rule it ships, with `--error-on-warnings`. The tree is also clean at `--diagnostic-level=info`, and `pnpm lint` FAILS on an info finding: `tools/lint.mjs` reads Biome's JSON summary and treats errors, warnings, and infos alike. It exists because `--diagnostic-level` controls what Biome displays rather than what it fails on, and most of the rules that bite here report at info, so before the gate they accumulated unnoticed until someone read the output. It takes paths, so `pnpm lint <file>` is the fast check while writing one.

**Fix the violation, do not turn off the rule.** This is the standing rule for this repo. Almost everything the strict preset flags has a real fix, and reaching for the config first hides work rather than doing it. Worked examples from the initial pass: `GM_*` interface members were renamed to `legacy*` and mapped at the boundary rather than exempting `useNamingConvention`; `import.meta.dirname` replaced `fileURLToPath` rather than exempting `noNodejsModules`; the build script dropped its dev flag entirely rather than exempting `noProcessEnv`; `export *` became explicit named re-exports rather than exempting `noReExportAll`; long functions were split rather than raising a threshold.

Exemptions are last resort and need a stated reason in `biome.json`. The current set is all structural, plus the rule configurations below it:

| Off | Where | Why it cannot be fixed |
|---|---|---|
| `useQwikValidLexicalScope` | everywhere | Demands closures be wrapped in Qwik's `$()`. There is no Qwik here. |
| `noDefaultExport` | `vite.config.ts`, `vitest.config.ts`, `loader/src/raw.d.ts` | Both tools resolve config only from a default export, and a module declaration for `?raw` imports has nothing but a default to declare. |
| `noNodejsModules`, `noConsole` | `tools/**`, `loader/build-runtime.mjs`, `loader/build-stage.mjs`, `addons/*/generate.mjs` | Node builtins are the purpose and console is the output channel. |
| `noSecrets`, `noMagicNumbers`, `useTopLevelRegex`, `noMisplacedAssertion`, `noExcessiveLinesPerFile` | `tests/**`, `addons/*/*.test.ts`, `addons/*/stage.ts` | Combos like `'Ctrl+Alt+Shift+Meta+KeyD'` trip the entropy heuristic and literal values are the fixtures; `.toThrow(/message/)` is the natural assertion; an assertion inside a shared helper is the point of the helper; and a suite is one subject per file, which splitting by line count would scatter. |
| `noExcessiveLinesPerFile` | `**/*.generated.d.ts` | A generated union is one name per line and its LENGTH IS CONTENT: the skill-icon union is 237 names across nine classes. The only ways under 300 lines are to drop names or to put several on a line, and the second destroys the reason for the format, which is that art landing or moving shows as a one-line diff. |
| `noExcessiveLinesPerFile`, `noHexColors` | `**/*.generated.css` | `stage/theme.generated.css` is a TRANSCRIPTION of a deployed game's own rules, so rewriting a colour into another notation would make it no longer the thing it claims to be, and a diff against the next reading would show every touched line as a change. |
| `noExcessiveLinesPerFile` | `addons/**` | An addon is one file BY DEFINITION: the manifest names a single `entry` and the loader evaluates it with `new Function`. There is nothing to split into. |
| `noReactSpecificProps`, `noSolidDestructuredProps`, `noJsxPropsBind`, `useSolidForComponent` | `**/*.tsx` | The Solid rule family, and there is no Solid here. `noReactSpecificProps` wants `class` where `noUnknownAttribute` wants `className`, so under `preset: "all"` the two contradict on the same attribute; the rest encode Solid's reactivity model, which preact does not share. The React-family rules stay on, so JSX is still linted. |

Configured rather than disabled: `useNamingConvention` runs with `strictCase: false`, since `URL` and `ID` are ordinary JS naming and vite-plugin-monkey's `downloadURL` is not ours to rename; `noExcessiveLinesPerFunction` allows 200 lines in `tests/**`, since a suite is a file's worth of cases rather than a function body. That test block sits AFTER the `addons/**` one in `biome.json` and has to stay there: a later override wins per rule, so an addon's own suite picks up the test relaxations rather than only the addon ones.

The standard for adding to that table is that the rule is IMPOSSIBLE to satisfy in that location, not that satisfying it is inconvenient. "I would have to restructure this" is the rule working.

When a suppression really is right at one site, use an inline `biome-ignore` naming the rule and giving a reason that says why the CODE is right, rather than widening the config. Note that an unused suppression is itself an error (`suppressions/unused`), so a speculative one fails the check: `new Function` is not flagged by `noGlobalEval` in Biome 2.5.5, and a suppression added for it had to come back out.

TypeScript runs `strict` plus `noUncheckedIndexedAccess`, `noImplicitOverride`, `noFallthroughCasesInSwitch`, `noImplicitReturns`, `noUnusedLocals`, `noUnusedParameters`, `noPropertyAccessFromIndexSignature`, `exactOptionalPropertyTypes`, `allowUnreachableCode: false`, and `allowUnusedLabels: false`.

## Rules that are load-bearing

- **zod must never reach the runtime bundle, and neither must semver.** `loader/src/shared/schema.ts` is the only zod dependant and `shared/gameversion.ts` and `shared/version.ts` are the only semver ones. The runtime imports their types with `import type`, which `verbatimModuleSyntax` erases. `loader/build-runtime.mjs` fails the build if either resolves there, and that guard has earned its place TWICE: `API_VERSION` when the addon lifecycle was wired, and `PERMISSIONS` when the install confirmation was, were each imported as a VALUE from `schema.ts` and each pulled zod and its fifty locale files into the page bundle. Both now live alone, in `shared/api-version.ts` and `shared/permissions.ts`. **The rule, not the two incidents: a runtime module that needs a CONSTANT the schema also uses gets its own module for that constant.** A value import of anything in a zod module drags the library; a type import costs nothing. The same reasoning is why update rows are computed in the host and carried over the bridge rather than derived in the manager: the comparison needs semver, and the case a hand-rolled one gets wrong is silent, since `1.10.0` sorts before `1.9.0` as a string.
- **A heal is attributed from `heal2`, never `heal`, and `cueOnly` is ignored by the FLAG.** Only `heal2` carries a `sourceId`; the plain `heal` event has a target and an amount and nothing to attribute it to. `heal2` also emits `cueOnly` records that exist purely to drive a sound and carry no healing, and the game's own comment says a meter must skip them on that flag rather than on `amount === 0`, because a genuine direct heal legitimately lands at 0 on a target already at full health. Inferring it from the amount drops those real casts too.
- **`net` is read-only.** No send API, no synthetic input, no automation. The game's terms prohibit automating play and it runs a bot detector whose heuristics are not public.
- **Never read `localStorage['woc_session']`.** It holds the account bearer token.
- **Outbound frames are redacted before any addon sees them.** The client's first frame on every socket, including every reconnect, carries that same bearer token as `{t:'auth-world-N', token, clientSeed}`. `redactOutbound` in `runtime/net/frames.ts` blanks it, matched on the field name rather than the frame type so a version bump or a new frame cannot slip past. Anything added to `net.onSend` goes through it.
- **A tap runs inside the game's own stack.** The socket hook's `send` override is synchronous in the game's call, so every tap is guarded. A throw in loader code must never break the frame the game was sending.
- **A fake must be the same KIND of thing the game hands over, not merely the same shape.** `__game.input.keybinds` is a class instance whose matchers read `this`, and a fake built from arrow functions closing over local Maps has no `this` to lose. That fake passed 947 tests while the loader threw on the first real conflict lookup and blanked the manager pane, because the manager reads conflicts during render. `tests/fakes/game-keybinds.ts` is a class for that reason. Anything reached through a game object is also called defensively: a future update can leave something callable in place that throws when called, and the cost of that has to be a missing warning rather than a dead screen.
- **The world types are a CLAIM about the game, and the loader checks what it can.** `runtime/world/game-types.ts` describes shapes in a repository this one does not depend on, must never depend on, and cannot compile against, so every read in `world/backend.ts` is an assertion rather than a derivation. `world/shape.ts` walks the live player once when the world goes live and reports every field that is missing or of the wrong kind. `tests/types-parity.test.ts` proves only that the loader and the published package agree with EACH OTHER, and they could be wrong about the game together.
- **A field is published only if it was found ON THE WIRE, and the shape check cannot enforce that.** The online client builds every entity with defaults and fills in what the snapshot carried, so a field the server never sends is present, of the right kind, and holds that default for the whole session. `checkEntityShape` passes it. `inCombat` is the worked example: it was published, `signature.ts` watched it, and the combat meter's first version read it to decide a fight was over, so it concluded every fight had ended and reset the total on every hit. `abilityCharges[id].maxCharges` is the same trap one level down and is deliberately NOT published: the server keeps the maximum to itself and the client zero-fills the field, so it is present, numeric, and permanently 0, and the game's own bar derives the max from a bundled ability table an addon has no equivalent of. Verify against `wireEntity`/`identityFields`/`dynamicFields` and the self payload in the game's `server/game.ts`, not against `src/sim/types.ts`. Currently NOT on the wire, and therefore not published: `inCombat`, `moveSpeed`, `onGround`, `jumping`, `castTargetId`, `stealthed`, `offhandWeapon`, `rangedPower`, `meleeHaste`, `rangedHaste`. Self-record-only fields are published and marked as such. `stats` and `weapon` were on that list and were wrong to be: both ride the self payload (`maybe('stats', p.stats)` and `maybe('weapon', p.weapon)`) and both are applied to the client entity, so both are published now. The mistake is worth keeping the shape of, because it is the one this rule cannot catch on its own: a `maybe()` field is delta-guarded, so it does not appear in every snapshot, and reading one live session's traffic mid-fight can show a field that is genuinely sent looking exactly like a field that never is. Read the SEND SITE, not only the wire.
- **`Entity.targetId` is the worked example of this rule catching a field ALREADY PUBLISHED, and the only thing that caught it was a live session.** It is emitted as `tgt` for players and bots only; a mob's selected target rides `aggro`, from `aggroTargetId`, and the send site says so in as many words. So on every mob in the game `targetId` is present, correctly typed, written by nobody, and permanently null. Nothing raises, nothing is missing, and a target-of-target display built on it works on players and is blank on everything it is actually pointed at. It was found by watching a mob visibly beating on the player never once appear to be targeting them, which is the reading no shape check and no type can do for you. Both fields are published now and `packages/types/entity.d.ts` says which is which; `world.unit('targettarget')` hides the difference, and hiding it is most of what that resolver is for.
- **An ability's ID and its DISPLAY NAME have diverged, and game 0.34.0 bridged ONE case of it rather than closing the gap.** `arcane_shot` is still shown everywhere in the game as "Fell Shot" (`arcane_shot: { name: 'Fell Shot' }` in the deployed i18n bundle, unchanged in 0.34.0). Skill art is filed under the ID; combat events carry the NAME. So an addon holding one cannot get the other, with exactly TWO exceptions. Your own spellbook is the first and is the only one that works in both directions: `world.abilities` closes the join either way. The second is `damage.abilityId`, which 0.34.0 added beside the display-name `ability` and the loader publishes there: a one-way answer for ONE emit, the primary direct hit, and the next rule is what it does and does not cover. It does reach ANOTHER PLAYER's ability, which `world.abilities.byName` never could, since damage records are world-visible and someone else's cast carries its own id. **Neither exception reaches a MOB's ability, which is most of what an addon watching a fight sees named.** The gate is a PARAMETER rather than a list of files, and is worth holding that way because a refactor moves call sites and not gates: every site that fills `abilityId` runs through `runEffects(ctx, p, meta: PlayerMeta, ...)`, the one exported entry point of the game's `combat/effect_dispatch.ts`, or through the two paths reached only from it, and a mob has no `PlayerMeta` to enter with. What a mob passes instead is a bare display label with no id in the content to carry at all: `'Gravebreaker'` in `encounters/nythraxis.ts`, `spell.name` for a hostile `petSpell` whose template declares a name and no id field, `null` on a swing. `combat/auto_attack.ts` is the file that LOOKS like the counterexample, since mobs auto-attack and it does pass an id; it does not, because that id is set on the player `weaponStrike` path only and the game's own comment says a plain swing leaves it unset. The two shipped addons sit on opposite sides of the spellbook exception and NEITHER reads `abilityId` yet: `combat-meter` reads events, so its names are right, and it recovers the id through `world.abilities.byName` and draws art for anything in YOUR kit and nothing for a mob's; `cooldown-bars` reads a cooldown map keyed by id, so its icons are right, and it takes the resolved length and display name off `world.abilities` too, leaving a title-cased id only where the ability is not in your spellbook at all. **Both are deliberate and neither is to be "fixed" by deriving the mapping**, which is still the answer everywhere `abilityId` comes back null, and that is most places. A first version slugified the name into an id and drew icons for the two hunter abilities whose names still happened to match, which reads as random rather than as a limit. The routes to a real mapping were weighed and rejected: the i18n bundle has all 380 pairs and is served, but behind a hashed filename discovered from `play.html`, as minified JS, per locale, which breaks on a bundler change rather than on a game change; and correlating a `spellfx` id with the damage that follows is learnable from the wire but a mispairing draws the WRONG icon, which is worse than none. `Aura` is the one shape carrying both, and only for abilities that apply one. Four addons carry a byte-identical title-casing fallback and all four still need it.
- **An event's `ability` is a display NAME, not an ability id, and the `abilityId` beside it is not always there.** Every `damage` and `heal2` emit fills `ability` from `ability.name`, `spell.name`, `abilityName`, or a bare label; only `castStart` and `spellfx` put an id in that field. The declared type is `string | null` for both, so nothing says which. This shipped a bug: `combat-meter` built an icon URL from the field and asked for `Measured Shot.webp`, while `cooldown-bars` worked because a cooldown map is keyed by real ids. What made it survive review AND a green suite is that the meter's `readable()` turns `measured_shot` and `Measured Shot` into the same label, so every assertion about a row passed either way and the fixture had been written with ids the wire never sends. Game 0.34.0 added `abilityId?: string | null` to the `damage` record for that exact class of failure on its own side: `IMPACT_ABILITY_CUES` in `src/ui/combat_sfx.ts` was keyed off the display label, so a display-only rename would have silently broken every entry. **It is populated ONLY for the PRIMARY direct hit, and the game's own instruction is that a client must fall back to `school` where it is not set.** Auto-attacks, DoT ticks, and echoed or fanned-out copies (Power Echo, Bladed Echo, Sweeping Strikes) omit it deliberately, so a dedicated impact cue fires once where an ability lands and never replays per tick or per extra target; a hybrid's dot shares the ability's id (Throat Wire's bleed is aura id `garrote`), which is why the tick is the emit that has to give it up. **Omitted means NULL rather than missing, so a consumer tests the VALUE and not the key.** All seven `damage` emits in the game's `combat/damage.ts` write the field unconditionally, so it rides every record and carries `null` wherever `dealDamage` was not given one, the evade arm included; contrast `attackAnimationStarted` on those same emits, which is spread in conditionally. The published type is optional as well as nullable, and the optionality is tolerance for a server predating the field rather than a case to expect. `heal2` has carried an `abilityId` for longer and it is a DIFFERENT promise: the applying AURA's id, on a HoT tick and on the application, absent from a direct heal. **An id is otherwise only safe to assume where the field is a map KEY** (`cooldowns`, `abilityCharges`) or where the emit site says `.id`. Where a name still has to become an id, slugify it and let the failure be cosmetic: the kit hides a bar's icon slot when the image 404s, so a name that does not round-trip costs an icon rather than a broken row.
- **Read the wire from the wire, not from the declarations.** They disagree silently and both directions have already bitten: the input ack rides `snap.self`, not the snapshot head, and an Entity carries `maxHp`/`resource` where the snapshot that delivered it said `mhp`/`res`. Reading the wrong one finds nothing, raises nothing, and looks exactly like a value that never changes. `tests/fakes/frames.ts` holds shapes captured from a live client; add to it from a real session rather than from `src/sim/types.ts`.
- **The bus refuses two things, and both refusals are the design.** `woc.bus` is how two addons cooperate at all, since an addon is one file with no imports. NOBODY RECEIVES THEIR OWN MESSAGES, on either form of `from`: an addon does not need a bus to call its own code, and self-delivery is the shortest possible loop. A SUBSCRIBER NAMES ITS PUBLISHER, `on(from, topic, handler)` rather than `on(topic, handler)`, with `bus.anySender` for the case where any will do. That PREVENTS squatting rather than detecting it, and the difference matters: the detecting version puts a `from` check in every subscriber, and that check is the one nobody writes. `from` itself is stamped in the hub from the fqid the surface was built with and the message is frozen, so a sender cannot claim to be an addon somebody decided to trust.
- **A synchronous emit is capped in depth, because a runaway one is a wipe.** Delivery is synchronous, which leaves A -> B -> A reachable even with self-delivery gone. Unbounded synchronous recursion hangs the tab, and a hung tab in a game is not a bug report. `MAX_DEPTH` stops it and `diag` says which addon and topic it stopped, and the counter is decremented in a `finally` so one throw cannot leave the bus muted for the rest of the session. This is also why there is no request-response and never will be: awaiting a reply from an addon that may be disabled, may never have been installed, or may simply not answer is a hang with no timeout anybody chose.
- **The unlock outline is an `outline`, and the bare density is why.** `density: 'bare'` strips its chrome by resetting `border` and `box-shadow`, at a specificity the unlock rule does not beat, so drawing the outline as either would put it on every frame EXCEPT the empty overlay the mode exists for. It is also drawn LOUDLY on purpose, with a wash over the frame's area rather than an outline alone: an outline around an empty bare frame is a rectangle around nothing, which says where a border is without saying there is anything there to grab. The first version was a hairline in the default border colour, which is a reasonable outline on a blank page and close to invisible over a game.
- **The official marketplace cannot be removed.** `canRemoveMarketplace` is called in the host, not the UI, so a hand-crafted call from the runtime still fails.
- **No host module may reach the runtime bundle.** The GM globals are declared ambient project-wide so the sandbox half can reference them, which removes the compiler's protection against the page half doing the same. `loader/build-runtime.mjs` inspects the esbuild module graph and fails on any input under `loader/src/host/`. Shared code goes in `loader/src/shared/`.
- **No Node module may reach it either.** `@types/node` is ambient project-wide because `tools/*.ts` needs it, so the compiler will accept `readFileSync` in a runtime module. `loader/build-runtime.mjs` fails the build on any `node:` or bare builtin import, the same way it does for host modules. The same ambience is why `runtime/dom-timers.ts` exists: `setTimeout` returns a `Timeout` under Node's types and a number in a browser, and the runtime only ever runs in a browser.
- **The local dev source is a build-time constant, not user input.** `LOCAL_ORIGIN` in `shared/marketplace.ts` is what puts `localhost` in the userscript's `@connect` list, and `normalizeMarketplaceUrl` rejects it like any other non-GitHub host. The set of origins the loader can reach is therefore still fixed at build time. `MarketplaceSource` is a union rather than an optional field so a caller building a URL has to say which kind of source it is looking at.
- **A marketplace id is re-derived on read, never trusted from storage.** Only the owner, repo, and ref a user actually chose are persisted; `fromStored` re-runs the same validation that accepting them did. The id is the storage namespace of every addon installed from that source, so a stored id a player could edit would be a way to point one source's addon at another's settings and data.
- **Installing an addon enables it, and the registry write is what starts it.** The body is cached at install so that enabling is never a network call, which means by the time the row exists the code is already on disk and there is nothing left for a separate enable step to defer. The player has already accepted a confirmation saying to install only what they would trust as a browser extension; not running it is a second decision they did not ask to make. `registry.changed` is what reaches the supervisor, through `runtime/host-events.ts`, so the start is the same path a toggle in another tab takes rather than a special case at the install site.
- **A failed addon stays enabled.** The supervisor records `failed` with the reason and leaves the registry alone. Auto-disabling would throw away what the player asked for to record something the loader already knows, and a failure caused by the game not being ready yet would then need a manual re-enable to recover from. Reload is what tries again.
- **Addon source is a function BODY, evaluated in strict mode.** No export, no registration call, `woc` in scope, and a `sourceURL` comment appended so traces name the addon rather than `<anonymous>`. Strict mode is prepended rather than left to the author: a sloppy-mode body turns an undeclared assignment into a property of the page's global object, which is one addon's typo becoming another addon's mystery variable, on a page shared with the game.
- **Shadowed globals are a guardrail and the message says so.** `runtime/shadow.ts` hands each addon proxies for `localStorage`, `sessionStorage`, `indexedDB`, `XMLHttpRequest`, `WebSocket`, and `__game` that throw and name the sanctioned API. `document.cookie` is the obvious next candidate and is deliberately NOT shadowed: it would mean handing addons a proxied `document`, which breaks every identity comparison in the DOM. A guardrail that subtly breaks correct DOM code is worse than the gap it closes.
- **The dev watcher polls BODIES, never the index.** A new addon directory or an edited manifest needs an explicit refresh. Index polling would emit a `market.changed` on every tick and repaint the manager continuously to report that nothing moved.
- **The dev server serves the loader itself, and that route is ONE EXACT PATH.** `resolveFile` guards a directory against traversal; `resolveLoader` matches `/woc-loader.user.js` and nothing else, so there is no second tree to walk in a server whose only real security property is that it has exactly one. The name lives in `tools/artifact.ts` because vite writes the file and the server hands it out, and a rename on one side would leave `pnpm dev` answering 404 while the build reported success. Installing over http rather than `file://` is deliberate: the file permission is off by default and moves between browser versions, so it turns "did the install happen at all" into the first thing to debug in a session that was about something else.
- **The dev server's index is generated per request and its `generated` stamp is an mtime, not a clock.** The ETag is taken over the response body, so a timestamp in it would make every index request a fresh body and the conditional GET would never answer 304.
- **`host/globals.ts` is the only module that names a GM function.** Everything else goes through `host/gm.ts`, which feature-detects on the shape `readGmSource()` returns. The ambient tampermonkey types declare the full surface, so they say nothing about what a given manager ships: a direct call is what breaks Greasemonkey, and the failure only shows up on a browser nobody tested.
- **Nothing but the handshake touches the `window` message channel.** Both halves drop their window listener the moment the port is transferred, and everything after that is on the port. A listener left behind would hand a second port to anything that replays the hello.
- **Nothing about an addon is written anywhere but that addon's own manifest, and the site and the README both read it from there.** Both publishers go through `tools/catalog.ts`, which is the same `readAddon` `pnpm validate` and `pnpm index` use, so nothing published can describe an addon the loader would refuse. The rule has been broken in the same shape three times and the shape is always a SECOND description: a `GAPS` map beside the catalog cards saying what each addon added, a heading and a body per featured addon on the landing page, and three hand-written paragraphs in the README. Each covered the two or three addons that existed the week it was written, none of them was wrong at the time, and all three still described that same handful when there were thirty-one. **The only thing either publisher decides is WHICH four addons get a picture**, in `tools/featured.ts`, shared so the site and the README cannot pick different favourites; everything on such a block is the manifest's own name, version, tags, description and alt text. `pnpm readme` is what keeps the README honest, and the workflow runs it so nobody has to.
- **The catalog a PLAYER reads is not the whole marketplace, and the difference is a tag rather than a list of ids.** An addon tagged `development` is a tool for addon authors: `dev-harness` ships, is in the in-game Browse, and is off the site's catalog page and out of the README's list. Derived from the manifest so an author tool added later is filtered the day it lands, and both publishers NAME what they left out rather than quietly shortening the count, because a site saying 31 where Browse offers 32 is a bug report waiting to be filed against whichever one the reader saw second.
- **A generated file is owned by the BOT or by the contributor, never by both, and the README is the bot's.** `marketplace.json` has never had a freshness test: it is regenerated on main and a contributor is not asked to run `pnpm index` before pushing. The README's addon section is written by the same job in the same commit, so it works the same way, and the test that once compared the committed file against a fresh render is gone. It failed twice in a day and was right both times: once because the count in an assertion was typed as a literal `31` while the repository held thirteen addons, and once because a commit dropped the section but kept everything else, which is a state the bot fixes on the next push and a test can only shout about. **What IS tested is the pair of markers**, since `pnpm readme` reads their absence as "no generated section here" and stops silently. The rule generalises: test the thing that would stop the generator, never the output the generator is responsible for.
- **Both derived files are regenerated by ONE job, and one job is what keeps them from racing.** `marketplace.json` and the README's addon section come from the same manifests and are both pushed to main by `.github/workflows/marketplace.yml`. As two workflows on the same event they would check out the same commit and the second push would be rejected as non-fast-forward, which is a failure that appears only on the day both files change. One job, one commit, and the title says which of the two moved, because it becomes a `CHANGELOG.md` line.
- **Never hand-edit `marketplace.json`.** It is generated by `pnpm index`. The dev server does not read it at all: `tools/serve-core.ts` builds its own index from `addons/*/addon.json` on every request, through the same reader `pnpm validate` uses, so a manifest saved mid-session is visible on the next refresh and the dev index cannot diverge from what CI would accept.
- **The runtime ships without a source map.** Inline is the only form that could work, since the host injects the bundle as `<script>` textContent and an external `.map` has no URL to resolve against, but that is a reason it must be inline rather than a reason to have it. It is 8x the bundle (149 kB to 1.18 MB) and the host re-injects the whole string on every page load, so it is a per-visit cost rather than a download-once one. `pnpm build:runtime:debug` turns it on. The flag is read from `argv`, never `process.env`, which this script deliberately has no dependency on.
- **A non-resizable frame is given its declared `width` as a WIDTH, and no height at all, and a ceiling was only half of it.** A frame nobody can resize is written by nothing but its position: `frame/interactive.ts` paints a size only where somebody can drag one, which is right for the height and wrong for the width, because a shrink-to-fit element is sized by its content in BOTH directions. The overflow half was found first. Wayfarer asked for 300 and drew at 693 the first time one of its own lines was a sentence, with its rows stretched across the extra width and the pins it is meant to sit beside covered by it, so `applyWidth` in `kit/frame.ts` wrote a `max-width`, on the reasoning that a frame NARROWER than it declared takes no more of the screen than it drew. **That reasoning was about a STATIC narrowness and the remaining failure is a MOVING one.** Under a ceiling the width still follows the content, so it changes whenever the content does: veinsight's header gains a clause while the player is harvesting, and the panel steps out and back with its rows reflowing, under the eye of the person doing the thing that caused it. Reported from a live session. Measured on the stage at veinsight's own declared 300: 120px with a short header, 263px with the clause, 120px again when it went. So it writes `width` now, and writes it whether the addon named one or took the default, since an addon that never thought about its width is precisely the one whose panel would otherwise move. **Nothing in Vitest can see any of this**, because happy-dom lays nothing out: the suite pins that a width is WRITTEN, and the stage is what proves the box holds still. There is deliberately no equivalent for the height, which is the failure the whole rule started from: a bounded frame clips itself rather than growing, and nothing on screen says a row is below the fold. Veinsight had already met the overflow half and worked around it by giving its own column `width: FRAME_WIDTH`; that workaround is gone, and it had to go, since the frame's padding is inside that number and 300 of content in a 300 frame clipped by 20.
- **A `.woc-bar` never shrinks, and the rule is one line of CSS with no test behind it.** A screenful of bars is a column flex container, which is the layout the kit exists for, and a flex item shrinks by default: with more rows than the frame is tall, every row was squeezed and the bar's own `overflow: hidden` then cut its second line off rather than the list scrolling. Lorebind found it at 24px against the 36px its rows needed. `flex-shrink: 0` in `styles/bar.css` is the whole fix, and it cannot be tested from Vitest for the reason that rule already gives: every `.css` import resolves to `''` there, so the agreement between a class and its rule is checked by running the loader. This is what the stage is for.
- **The tap-target floor is a TOUCH rule, and reading it as a universal one made every loader panel a third larger than the game beside it.** The game holds 16px type on a 40px target under `@media (pointer: coarse)` and nowhere else: `base.css` floors every focusable control there, with a comment recording that the number is 16 because iOS Safari auto-zooms below it and ignores the viewport scale-lock; `components.css` gives `.ui-dd-item` its 40px in the same query, noting that the global floor covers input/textarea/select and therefore misses a custom select trigger, which the kit's `picker.ts` is; `hud.mobile.css` gives the bank tabs theirs under `body.mobile-touch`. On a DESKTOP the game runs 11px to 13px throughout: `.bank-tab` and `.delve-tab` are 13px on 7px of padding, `.btn` is 12.5px on 6px, `.ui-dd-item` is 12px on 5px, `#tooltip` is 12px, `.panel-title` is 15px, and `.x-btn` is 14px with no minimum at all. `comfortable` applied the touch numbers unconditionally, so a loader window sat beside a game window at roughly 4:3 and read as a different application drawn on top of the game. Reported from a live session, with Lorebind and Ledgerline open over the action bars. The floor is not gone: `ui/styles/touch.css` is the same query, concatenated LAST so it beats the density variants at (1,2,0) and reaches a compact frame as well as a comfortable one. **What follows for an ADDON is that hand-sizing a kit control defeats it**, because an inline style outranks every selector a stylesheet can spell; satchel wrote 13px on a 24px floor onto its two fields and lorebind wrote 26px onto its quality chips, both to escape the old default, and both were silently opting out of an accessibility rule on a phone. Change the PADDING, never the font size or the height. **The rule generalises past this fix: a number copied out of the game is only as true as the query it was copied from.**
- **Frame density is an enum, and the default is the game's own scale.** `ui.frame`/`ui.window` take `density: 'comfortable' | 'compact' | 'bare'`. Comfortable is what the game draws its own windows at on a desktop and is the default, so an addon that has not thought about it looks like part of the game; compact is tighter than the game's own panels, for a dense readout an addon GLANCES at. Compact used to be the escape hatch from the touch floor and every dense readout had to take it; with comfortable retuned that is no longer a reason to, and an ordinary window should stay comfortable. An enum rather than `compact: true` because the axis has more positions in it and a flag set turns into a matrix nobody can reason about. That prediction is now spent: the borderless overlay this rule named as the next request IS `bare`, which drops the panel, the padding and the title bar and keeps everything else, and it cost one enum value rather than a second primitive. `ui.window` refuses `bare` ONLY, and falls back to comfortable when it sees one, because a window's close button lives in the title bar that `bare` removes and a panel the player cannot dismiss is worse than one drawn more heavily than asked for; it honours `compact` normally (`frame-chrome.ts:44`). An earlier version of this line said a window ignores density outright, which overstates what the code does and sent a reader looking for a bug that was not there.

**Which of the two an addon reaches for is decided by the ARIA ROLE, and everything else people reach for to tell them apart is decided elsewhere.** `roleFor` is the whole of it: a window is `role="dialog"`, a thing the player OPENED, and a frame is `role="group"`, HUD furniture that lives on screen. Three things that look like the difference are not: the close button is `closable` and works on either (`closeFor`, gated on density rather than on chrome, and a window merely defaults to having one); the game's `panel` border and background are worn by any non-`bare` density, window or not; and resizing is its own option. The only other thing chrome decides is that a window refuses `bare`, which follows from the role rather than standing beside it, since a dialog with no chrome is not a dialog.

So the rule is: a HUD surface the player toggles is a `frame`, and a surface the player opens to read and then dismisses is a `window`, because that is what a screen reader will announce and it should be true. Every addon built so far binds a toggle and none binds an open, so every one of them is a frame, and a frame that wants a mouse route to dismiss it passes `closable: true` rather than becoming a window. Reported from a live session as "many addons use ui.frame and not ui.window, should all addons use ui.frame then", and the answer is yes for everything that toggles. A bare frame is dragged by its own CONTENT, which is also why the unlock mode exists: an overlay whose list is empty is zero pixels, and zero pixels cannot be grabbed. An unrecognised value falls back to comfortable, never to compact: the failure mode to avoid is a typo silently dropping the floor. The variant also reaches `.woc-btn` and `.woc-tab` inside the frame, which is what makes reusing those families the right move for an addon instead of restyling its own.
- **A bar's fill is tinted by SCHOOL, and the palette is the game's.** `ui/kit/bar.ts` takes `school` as an axis separate from `tone`: tone is urgency (a cooldown row going warm as it comes up), a school is what kind of damage a row is made of, and folding them into one enum would make `tone: 'frost'` and `tone: 'danger'` look like alternatives to the same question. The colours are `--color-debuff-*`, which the game already publishes for its own debuff borders and the loader inherits like `--gold`, so a tinted row matches what the player reads for that school on an aura icon; nothing is invented and no addon may pass a colour, because two addons colouring by school should look the same. Tone wins over school where both are set, by SOURCE ORDER in `styles/bar.css` at equal specificity, which is why the two groups there carry a note not to reorder them. **Rank and share were both rejected as the colour axis**: a row already encodes rank by its position and share by its fill width, so either would be a third encoding of a fact already on screen, and rows would swap colours whenever the ranking shifted, which is exactly when you want to keep tracking one ability. `combat-meter` colours this way because it cannot show ability art at all.
- **A DROPDOWN IS THE KIT'S MENU, and a native `<select>` is not usable here at all.** Its popup is drawn by the operating system: outside the document, in the system font, beyond every rule the loader has, so an addon's filter row opened a white system list in the middle of a dark fantasy HUD. The game reached the same conclusion for itself, and `.ui-dd` in its own stylesheet is a button, a caret and a menu with the chosen row in gold, which is what `kit/picker.ts` now is. It is the EXISTING menu rather than a second popup, because `ui.menu` already owns the four ways one has to close and a hand-rolled dropdown gets three of them right; `MenuItem.checked` is what a choice-menu marks its row with, drawn in the accent and announced as `aria-checked`. TWO renderers, like the close mark: `kit/picker.ts` for plain DOM and `manager/picker.tsx` for the manager's preact, over one caret geometry in `kit/caret-glyph.ts`. The manager's own two selects went with it, which is what `mount.ts` hoisting `buildSurfaces` above `mountManagerPair` is for: the manager needs the one menu, and a second one would be the drift `field-shape.ts` exists to prevent. **A suite that drove the old control still passes and proves nothing**, which is the trap here: a `<button>` carries a `value` property too, so assigning one and reading it back is green while the manager is never told anything. `tests/fakes/controls.ts` drives the real thing and `menuService` in `tests/fakes/ui-deps.ts` is why every manager suite has a real menu to drive.
- **ITEM QUALITY is a third axis of the same kind, and the two tables it needs live apart on purpose.** A tier is what a player picks an item out of a grid by before reading a word, so `ui.bar` and `ui.tile` take `quality` beside `tone` and `school`, and `woc-quality-<tier>` is published as a class an addon may put on anything it owns, the way `.woc-btn` and `.woc-tab` already are. Lorebind held six hexes of its own until this existed and every other addon that draws an item would have held the same six. **The palette is the game's and is NOT a token**: it publishes `--color-quality-default` for an item it ranks at no tier and hard-codes the six, in TWO tables that differ at one tier, `QUALITY_COLOR` in `src/ui/icons.ts` for a NAME and the `.q-*` rules in its own sheet for a BORDER, where common is white as a word and a dimmer grey as an edge. So both are transcriptions with the same standing as the item table an addon has to carry. The name table is in `styles/quality.css` with the two families that read it and the border table is in `styles/tile.css`, and the split is the CASCADE rather than taste: `.woc-tile` sets `border` as a SHORTHAND, so a tier declared in an earlier sheet is overwritten wholesale, and one declared after the school and tone groups would win a border that belongs to urgency. The three groups in `tile.css` are therefore one ordered run, tier then school then tone, each winning from the one before. Nothing under Vitest can see any of that, since every `.css` import resolves to `''` there: the suites pin the CLASS and the order was checked by running the loader on the stage, which is what the stage is for.
- **There is ONE close mark, in `ui/kit/close-glyph.ts`, rendered two ways.** `×` is MULTIPLICATION SIGN: it inherits the title bar's serif font, so it renders at whatever weight and optical size that font gives it, thin and off-centre and visibly not the mark the game's own close buttons use. It is a stroked path now, using `currentColor` so the existing hover rule still reaches it, with the `aria-label` kept on the button because a path cannot be read aloud. It was written in TWO places, a `textContent` in the frame builder and a `closeGlyph` entry in the manager's strings, so replacing one shipped a loader with two different close buttons on screen at once, reported from a live session. The geometry now has one home and two renderers, because the frame builder is plain DOM and needs markup while the manager is preact and would otherwise need `dangerouslySetInnerHTML` for something that does not need it. Both `tests/ui-kit-frame.test.ts` and `tests/manager-render.test.tsx` assert against `CLOSE_PATH` by name, so a renderer that goes its own way fails there rather than in a screenshot. **A glyph never goes in a strings module:** strings are text a translation pass would touch, and a translated close mark is nonsense.
- **CSS text is not readable from a Vitest suite.** Every `.css` import resolves to `''` under vitest (`LOADER_CSS` measures 3 characters, the joining newlines), and `?raw` does not change that because vite's own CSS handling wins. So a suite can pin the class a module WRITES but not the selector the sheet declares; reading the file would need `node:fs`, and `noNodejsModules` is not exempt in `tests/**`. The agreement between a class name in `ui/kit/` and its rule in `ui/styles/` is checked by running the loader, not by the suite. Do not widen the exemption table for it.
- **Window order is ONE service on the root, never per window.** Loader windows are absolutely positioned siblings with no z-index, so before `ui/kit/stacking.ts` overlap fell out of DOM order and clicking a buried window left it buried: with the manager and two addon frames open, the one behind was unusable. One capture-phase `pointerdown` plus `focusin` on `#woc-addons`, resolving `closest('.woc-window')`, covers the manager and every addon frame with no per-surface wiring, and any window a future feature adds participates the day it lands. Capture phase because a child that stops propagation must not be able to bury its own window. `focusin` because tabbing into a buried window and staying buried is the keyboard version of the same bug. A frame is also raised when BUILT and when SHOWN, since a window nobody has clicked holds no z-index at all and would open under everything clicked so far; hiding is deliberately not a stacking event. The manager raises itself from `show()` in `ui/manager/index.tsx`, finding its own window by `[data-woc-manager]` since `.woc-window` is every addon frame too, and it raises even when the window was ALREADY open. That was a wrapper around the manager `mountUi` returned, and the wrapper was the bug: every route in is outside the root (two buttons in the game's own DOM, a userscript menu command, the host reporting an install), the two in-game ones hold the manager passed to `buildKit` rather than the wrapped one, and pressing Addons with an addon frame on screen opened the manager behind it. Reported from a live session. **The rule the wrapper got wrong is that raising belongs to the act of SHOWING, not to a caller**, which is the same place a frame raises from; a per-route wrapper is a list of callers that has to be complete, and it was not. **The counter renormalises at `WINDOW_Z_CEILING` rather than running away**, so the overlay bands in `styles/kit.css` (toasts, modal, tooltip, which start one above it) are above EVERY possible window rather than above the ones anyone expects; dead windows are dropped on the way. Keep the CSS values and the ceiling in step.
- **A window's placement rules are pure, and its gestures are not.** Everything a player can notice (a window cannot be dragged somewhere it can never be dragged back from, a restored position survives a smaller monitor, a persisted box is validated before it reaches a style property) lives in `ui/frame/geometry.ts` with a Node test. interactjs handles pointer capture, touch, and edge hit areas, and nothing else. A NaN reaching a style property drops the declaration silently rather than raising, which is why the persisted box is parsed rather than trusted.
- **Nothing in the game's HUD exists until world entry.** `#ui`, `#options-menu`, the micro-button rail and everything in it ship inside `<template id="game-ui-template">` and are cloned into `document.body` only when the player enters the world; `#game-version` is the sole anchor outside it. A one-time lookup at DOMContentLoaded finds none of them and fails silently, which is exactly what happened. Injections wait through `ui/hud-mount.ts`, on a `childList`-only observer: the clone is one fragment insert of direct body children, and a subtree observer would run a selector against every HUD mutation for the rest of the session. Reading `index.html` for this is a trap, since grepping an id shows the element but not the `<template>` that encloses it.
- **Every game selector goes in `runtime/ui/anchors.ts`.** They are the external surface the whole project rests on and the game owes us nothing for any of them, so a game update that moves one has to be a single edit. The manager's Diagnostics pane resolves the table live, which is what makes drift visible before an addon author reports it as a bug.
- **Addon frames are hidden whenever the game HUD is not in the document, and the default is hidden.** The root being a sibling of `#ui` means a HUD re-render cannot take addon UI away, and the cost is that nothing takes it away when the HUD legitimately goes: a live session found a meter window sitting over the landing page's PLAY button after a logout. `ui/root.ts` puts `NO_HUD_CLASS` on the root at mount and `ui/mount.ts` clears it from the HUD presence signal, so the state that needs no event to be correct is the safe one. That matters because a frame with a saved visibility is restored the moment its addon starts, which is at document-start on the landing page. The rule names `.woc-addon-frame`, never the root's children: the manager has to stay reachable with no game at all, since it is how a player finds out the loader is broken and one of its three routes in is host-side. Addons keep RUNNING before world entry by design (they subscribe and prepare while `world.ready` is pending); what they must not do is draw over the game's own pages. `whenHudMounts` therefore reports presence falling as well as rising, and `attached()` means "is the HUD up now", not "was it ever".
- **The root is a sibling of `#ui` and is NOT A LAYER; the two bands inside it are.** `#woc-addons` is `display: contents`, and `ui/root.ts` puts a `woc-hud-band` at `z-index: 5` and a `woc-overlay-band` at `100001` inside it. The root used to be the layer, one z-index above the game's own ceiling, and that single number was the whole reason **the game menu opened UNDERNEATH an addon frame**: `#options-menu` is a `.window` INSIDE `#ui`, so one z-index above `#ui` is one above every window the game has, the bags and the map and the spellbook included. There is no slotting between them from outside, since `#ui` is one stacking context, so the answer is two bands. `display: contents` is what makes it possible and is load-bearing: `position: fixed` ALWAYS creates a stacking context whatever its z-index, so a root with a box traps both bands in one layer again. **Which band a thing goes in is the frame/window distinction the kit already draws**: a frame is HUD furniture and goes in the hud band, under any window the player opened; the manager, menus, toasts, modals, the banner and the tooltip go in the overlay band, above everything. World anchors are hud, because a label over a mob is not something the player opened. The price is that the game's chat and action bars now cover an addon frame too, and that is the right way round: those are controls the player needs. Two consequences that are easy to miss. `#woc-addons > *` became `#woc-addons :where(.woc-hud-band) > *`, and the `:where()` is deliberate: it holds the rule at (1,0,0) so `#woc-toasts` and `#woc-tooltip` in `kit.css` still turn the pointer back off on source order, and a band class weighed normally would silently outrank both and put a dead strip across the top of the world. It is also TWO rules rather than one `:where(a, b)`, because the build's scoping guard splits a selector list on commas and reads the second half as unscoped. And an addon reaching `frame.el.parentElement` now finds a band rather than `#woc-addons`, which is unsupported either way but is the one thing this moved under anybody's feet.
- **A frame's `pointer` decides how much of the player's controls it takes away, and a bare one is `content` by default.** The game binds the world's `mousedown` and `wheel` to the CANVAS, so an element over it does not cover a click, it consumes the gesture: targeting, right-drag camera look and wheel zoom all stop inside that box. Nothing can forward them on, because the loader's root is not an ancestor of the canvas and a synthesised event is both untrusted (the game runs a bot detector) and against the no-synthetic-input rule. `pointer-events` is therefore the only lever, which is why this is an option rather than a fix. `auto` is the whole box; `content` makes the box transparent and leaves what the addon DREW live, so gaps and dead width fall through while rows keep hover and tooltips; `none` is inert. The default is per density because the densities mean different things: a panel with holes in it is a panel that sometimes ignores the player, while a bare overlay's empty half is INVISIBLE, and solid by default it is a rectangle that swallows clicks while showing nothing. That was not hypothetical: `interactive.ts` writes an explicit width and height only for a RESIZABLE frame, so an empty resizable bare strip was exactly that rectangle. **This is the game's own idiom, not an invention**: every read-only overlay it draws is `pointer-events: none` (`#nameplates`, `#perf-overlay`, `#aura-overlays`) and the aura overlay takes the pointer only under its `.placement` class, which is its arrange mode. The unlock mode is ours and forces every frame back to `auto` for the same reason. What follows, and is one sentence rather than a second rule: with `content` you grab the frame by something it drew, so a drag or an edge resize works over a row and goes to the game over empty space. **Verified in a real browser over CDP rather than reasoned about**, because the load-bearing question was whether interactjs still starts a drag from a child of a `pointer-events: none` element: it does, the press lands on the row and matches the interactable by bubbling. A tooltip cannot survive `none`, and the hit-test-on-pointermove workaround was rejected: it re-derives what the browser already knows, on every move, while the player is playing.
- **The addon root is a sibling of `#ui`, and its stylesheet is unlayered.** The HUD rebuilds its own subtree, so a root inside it would be swept away with whatever re-rendered. Every game rule lives inside `@layer base` or `@layer components`, and an unlayered rule outranks any layered one whatever the specificity, so addon styling survives a game update that adds a layer or reorders the ones it has. The flip side is that these rules also outrank the game's, so they stay scoped to loader-owned elements. `loader/build-runtime.mjs` enforces that, and the scoping rule has ONE exception with a different check behind it: a `@keyframes` block's interior is `from`, `to` and percentages, which are positions on a timeline and match no element, so the build strips those blocks before reading selectors. What it checks instead is the animation NAME, which is global to the document rather than scoped to a subtree and must therefore start with `woc-`: an unprefixed one shadows a game animation of the same name, and the symptom is the game's own element animating wrongly.
- **The manager has three independent ways in, and one of them is not in the game.** The game-menu entry and the rail button both live in game DOM and can be taken away by a game update; `GM_registerMenuCommand` is host-side and cannot. That command is registered whether or not the runtime ever connects, and a failed bridge handshake costs the registry rather than the UI, because the manager is how a player finds out the loader is broken.
- **Anything that returns a promise rejects rather than throwing.** Comlink turns a synchronous throw into a rejection, so the bridge hides the difference and a direct caller does not. The manager holds the registry directly when it can, so a `pending()` stub that throws is a real failure mode the bridge tests cannot see.
- **The keydown listener claims a key ONLY when a bind matched.** The loader's dispatcher runs in the capture phase, ahead of the game's own handler, so `stopImmediatePropagation` is a decision about whether the game gets to act at all. Calling it eagerly quietly degrades the controls of a game the player is still playing, and nothing reports it. The editable-element guard is deliberately WIDER than the game's, which checks only input and textarea: declining where the game would act costs one keystroke, acting where the game declines eats a character out of something the player is typing.
- **Conflict detection reads the game's LIVE keybind profile, not localStorage.** `__game.input.keybinds` carries the game's own matchers and every DEFAULT binding. The stored blob holds only what the player explicitly saved, so on an account that never opened Key Bindings it is empty and every key reads as free. Storage is the fallback, and the reading carries a `source` so the manager can say the answer is incomplete rather than presenting it as clean. Held actions (movement) match the bare code with modifiers ignored while edge actions match the whole chord, and the stored string does not say which it is, so the fallback over-reports on purpose.
- **Skill art has a SERVED manifest, and it is the second endpoint of its kind.** `/ui/skills/<class>/mapping.json` lists which ability ids ship a painted `.webp`: nine files, one per class, with no index over them, so the class list is written out in `tools/icons-core.ts`. `pnpm icons` renders them into `packages/types/icons.generated.d.ts` and `runtime/ui/kit/skill-art.ts` reads one per class at run time, exactly the split `pnpm cues` and the sound engine make over the cue pack. Every OTHER ability's icon is composited on a canvas by a module that is not on `__game`, so it exists in the game and has no URL an addon can point at. The reason to read the manifest is not the requests it saves but the ambiguity it removes: without it a blank icon slot means either "no file exists" or "the loader built the wrong id", a 404 cannot tell those apart, and a session went into chasing the second while looking at rows from the first. The manifest carries `{abilityId, sourceFile, output}` and NO display name, so it cannot recover an id from an event's ability field.

  `pnpm icons` reads LIVE by default, like `pnpm cues`, because the published types describe what most players are running. **Do not union the channels.** They diverge in BOTH directions, measured across all three: pbe carried 318 ids to live's 237, live carried `judgement` that pbe had already dropped, and pbe2 matched live exactly. A union would autocomplete names most players' games have no file for. Narrowing costs autocomplete and nothing else, because the RUNTIME reads the manifest from whichever host the player is on and the published union is open where it is used, so a pbe-only ability still resolves there.
- **Item art has a served manifest too, and its NAME field is provenance rather than the item's name.** `/ui/items/mapping.json` is the third endpoint of the kind `pnpm cues` and `pnpm icons` already read, and it is ONE file rather than a per-class fan-out, so a bag grid of 72 cells costs one request. `pnpm items` renders the id union into `packages/types/items.generated.d.ts` and `runtime/ui/kit/item-art.ts` reads the deployed one at run time, with the same optimistic-until-known contract `skill-art.ts` proves out. The channels are NOT unioned, for the reason the skill manifests are not: measured 2026-08-02, live and pbe carried 562 ids and pbe2 563. It carries two lists, `entries` (curated, with a name) and `generatedBatches` (ids only), which do not overlap and whose union is exactly the `.webp` files in the directory. `iconSize` is the shape check, standing in for the `class` field the per-class manifests have: without it a payload that is not this manifest reads as a manifest naming nothing.

  **The name is the ART SOURCE name and drifts from the game's display name.** The game's own gate on the field is that it is non-empty; nothing compares it against the item table, and a content rename rewrites the table and leaves the art provenance alone. Measured against game 0.33.0: 281 of 303 agree and 21 do not. So it is published as `ui.icon.itemArtName`, labelled, and is deliberately NOT generated into the types: a name that looks authoritative and is wrong one time in fourteen is worse than no name. There is no `world.itemName` and there must not be, because a name API implies a source for one that is right and there is none: the item table is bundled into the game's own chunk. **Every item without art is a WEAPON, and a weapon's art is unreachable and always will be**, filed under a MODEL name through a table the game does not serve. That is now the WHOLE of the gap, and it is structural rather than a backlog: the game derives its own art set with `if (item.kind !== 'weapon') ITEM_IMAGE_IDS.add(item.id)` over live content, so a non-weapon added tomorrow is in it that day, and `ITEM_ART_PENDING`, which enumerated the art it had commissioned and not yet committed, is EMPTY as of 0.34.0. **That every item without art is a weapon is true of today's content and is NOT a rule to code against, because the pending gate is still live.** `itemImageUrl` checks `ITEM_ART_PENDING` first and returns null on a hit, so a non-weapon CAN ship with no art, and one release ago it did: at 0.33.1 that set held exactly 101 items, which is the number the earlier version of this line quoted. It refills whenever content lands ahead of its art. So read "no art" as "no art" and never as "is a weapon", which is why an addon reporting art coverage keeps the reading one-directional: the runtime reads the manifest from whichever host the player is on, so a pbe player running ahead of live can hold an item whose art has not shipped anywhere yet. Measured at 0.34.0: 134 weapons out of 815 items, against 682 manifest ids. Those counts move with content and the shape does not, which is the half worth quoting; an earlier version of this line quoted only the counts, said 134 of 797 with another 101 merely awaiting art, and the second number went to zero in one release. The manifest is also NOT a subset of the item table: `backpack` is in it and is not an item at all, the implicit 16-slot bag the bag bar draws first, which can never be looted or equipped and therefore has no def. One id today, but anything joining the manifest against items has to tolerate a miss rather than read one as a bug.
- **A cue is not a file.** The game serves `/audio/sfx/runtime-pack.json`, which collapses a numbered family into one cue with variants: 432 files are 220 cues, and it also carries the gain the game normalized each clip to. Take cue names and tuning from the pack. A directory listing would offer addon authors 212 names that do not resolve, and would play every cue untuned. `packages/types/cues.generated.d.ts` is that same pack rendered as a union for autocomplete, written by `pnpm cues` and never by hand. It stays an OPEN union (`KnownCue | (string & Record<never, never>)`): the set is content, a game release adds to it before these types catch up, and a published type must not be able to break a working addon.
- **`addEventListener` capture uses the OBJECT form, never the boolean shorthand.** Node's `EventTarget` accepts a boolean on add and then ignores it on remove, so the shorthand leaves the listener attached and the teardown silently does nothing. Browsers honour both, which is exactly what makes the shorthand the version that looks fine until it is not.
- **The four storage namespaces are split on TWO independent axes, ownership and scope.** `addon:<fqid>` is the addon's own KV, account-wide; `char:<fqid>` is the addon's own KV for ONE character; `config:<fqid>` is loader-owned settings and keybind overrides; `ui:<fqid>` is loader-owned per-character frame state. Ownership is why `config` and `ui` are not in `addon`: an addon calling `storage.set('values', ...)` would otherwise become the addon whose settings never persist, and `storage.keys()` would report loader data as the addon's own. Scope is why `char` is a namespace rather than a prefixed key inside `addon`: sharing it would put one character's keys in front of `storage.keys()` for every other character, and would let an addon's own key name collide with the derivation. The two axes are independent, which is the thing to hold on to when a fifth is proposed: `addon` and `char` share an owner and differ in scope, `ui` and `char` share a scope and differ in owner.
- **Per-character state is keyed on realm plus character name, never on `pid`.** The pid from the `hello` frame is the sim's entity id for one session and is reissued on the next, so anything keyed on it scatters across a new set of storage keys every login and reads to the player as nothing ever having been saved. `perCharacterKey` in `shared/storage-keys.ts` is the ONE derivation, shared by the loader's frame state and an addon's `storage.character`, because "per character" has to mean the same thing in both: a frame and a data key that disagreed about whose they are would be two halves of one addon restoring for two different people.
- **A per-character READ waits for the character and a per-character WRITE refuses to.** It looks inconsistent and is not, and both halves matter because an addon's first line runs at document-start, on the landing page, where there is no character and therefore no key. A read's answer is determined when it RESOLVES, so holding it until world entry hands back the data of whoever actually logged in, which is right whichever character that turns out to be. A write's payload was determined when it was CALLED, so holding one would take a value computed before anyone knew whose it was and store it against whichever character the player then picked: not a delay, but one character's data written onto another's, silently. `woc.storage.character` therefore rejects a write before world entry and names `world.ready` as the gate. Dropping it instead, which is what `kit/frame-state.ts` does, is right THERE and only there: frames are hidden before world entry, so there is provably no gesture to record, and without that argument a dropped write is a promise that resolved to say something happened.
- **A tooltip whose anchor leaves the document is the KIT's problem, not the addon's.** `pointerleave` never fires on an element removed while the pointer is over it, so a tooltip on a row an addon dropped floated in the middle of the frame with no event able to clear it: reported from a live session, cooldown-bars, a finished cooldown. The attachment outlives the element too, so a list that rebuilds rows leaks one registration per row per rebuild into the addon's bag. `ui/kit/tooltip.ts` owns both. The visible one is a MutationObserver that runs ONLY while a tooltip is shown, scoped to the loader's root rather than the document, since addon DOM is there and the game's HUD is not; a body-level subtree observer would wake on every HUD change at snapshot rate to answer the same question. The leak is swept on the next `attach`, which is the moment a rebuild is definitely happening, rather than by an always-on observer. **An attachment is not reaped until it has been seen CONNECTED**, because an addon legitimately attaches before inserting (create the row, describe it, append it) and reaping everything disconnected would kill exactly those; the observer therefore also checks the shown anchor directly, which is the one case the sweep cannot reach. None of this is on the public API: an API where an author has to pair an attach with a detach on a lifecycle the loader owns is an API whose leaks belong to whoever forgot.
- **Everything an addon creates goes in its disposal bag, and a pending promise resolves rather than hangs.** Disable is hot, with no page reload, so a bare `setInterval` runs forever against DOM the loader has already removed. An open modal or a key-capture prompt torn down at disable resolves with a dismissal value: a rejection would run the addon's catch at exactly the moment it can no longer safely create anything.
- **The manager's reading path fetches AT MOST ONCE A SESSION, and the once is not optional.** `market.list`, `registry.list` and `registry.updates` all answer from what the host already holds, and Refresh is the only control that always fetches. An update badge that decided to fetch would put a request per marketplace in front of every open of the window, which is the version of the feature that gets switched off. The three marketplace panes share one `catalog-store.ts` for the same class of reason: three copies of "the source list plus the installed set" would go out of date independently, and Browse would offer an Install for a source the Marketplaces pane had already removed. **The half this rule originally missed is that nothing ever paid the once.** The index cache in `host/market-indexes.ts` is per session, and every call that filled it was a player pressing something, so on a fresh install AND after every page reload Browse drew "no marketplace has been read yet" until the player found Refresh, and `registry.updates` compared installed addons against no rows and answered that nothing needed updating: a false all-clear, which is the worse of the two because it looks like an answer. `market.ensure` closes it, awaited AHEAD of the three reads in `catalog-store.ts` rather than beside them, since all three read the cache it is still filling. The once-per-session refusal lives in the host, not the store, so a second caller cannot turn it back into a fetch per open; a source whose read FAILED counts as read, or the retry would be the doomed request in front of every open that the rule exists to prevent. The reason this is affordable at all is the fetcher's ETag cache: the seeding read of a second session is a 304 with no body.
- **A companion is a NOTE with a route, and the two halves it carries live in two keys for a reason that is not taste.** `companions` is the id and `companionReasons` is one sentence per id saying what that addon ADDS. The second key exists because a description was doing that job: satchel's said "install an addon that publishes item prices and it adds up what a vendor would pay", which is read before the player knows the companion exists, cannot say whether they have it, and goes stale the day the relationship changes. **It could not be a richer shape for `companions`, and that is the load-bearing half.** A marketplace index is parsed as ONE `z.array(MarketplaceEntry)`, so a single entry an older loader cannot read fails the whole index and takes that source dark for every player still on that loader; an unrecognised KEY is dropped, which is the compatibility the manifest docs already promise. The tie between the two is enforced rather than trusted (`AddonManifest.refine`: every reason key must be a named companion), because two keys describing one relationship is exactly the shape that drifts. **The field still gates nothing, and the actions it grew are not a second path to anything**: Enable is the Installed pane's own toggle pointed at another row, Get sets the same `confirming` state the row's own Install sets so the SAME confirmation renders, and Find it moves to Browse with the search filled. The comment in `companions.tsx` said "a NOTE and never a control" and its reasoning (a second install path is a second thing to keep honest) is why every action is a jump into a control that already existed rather than a new one. Two things follow that are easy to get wrong. The pending row is resolved against EVERY row rather than the filtered ones, since a player pressing Get has almost always searched for the addon that named the companion rather than for the companion. And Browse's search is held by `ManagerApp` rather than by `BrowsePane`, because Find it switches tab and a pane that owned its filter would be rebuilt empty by the switch, which is the one thing that jump exists not to do.
- **A pin means "stop offering", never "install that instead".** A marketplace serves one version per ref, so there is no older body to go back to. `registry.setPin` fetches nothing; it takes the addon out of the update list and out of "update all". The row stays visible carrying its pin, because the only thing a pin needs a UI for is saying that an update exists and that the player's own decision is holding it back.
- **The contents-API fallback is reached only on a 404, and only for a repository.** A 403 is the unauthenticated rate limit, and answering it with one request per addon would spend what is left of the hour discovering there is no quota. A repository whose `addons/` listing 404s too is one the loader cannot see at all, so the error reported is the one about the index the player was looking for. A repository with more directories than fit in the quota is REFUSED rather than truncated: reading the first forty and presenting them as the source's contents would be a silent lie about what it offers.
- **`MarketApi.setRef` moves where a source reads from and never its id.** The id is derived from owner and repo, so everything installed from that source keeps its fqid and therefore its settings, keybinds, and data. The cached rows are dropped on the way, or a failed read of the new tag would leave the previous tag's addons on screen under the new tag's name.
- **Declared permissions are a disclosure, not a boundary, and the pane says so.** Addon code runs in the page realm with the page's globals in scope, so a manifest that declares nothing is not thereby prevented from doing anything. The install confirmation shows the declared list next to that sentence: a permission list with nothing beside it reads as a sandbox, and there is not one.
- **`@name` and `@namespace` are FROZEN, and freezing them is the same rule an addon id has.** A userscript manager keys a script's identity, and therefore its whole GM value store, on that pair. Changing either is not a rename: it is a new script with an empty registry, so every player loses their installed addons, settings, keybinds and saved window positions, while the old script sits alongside it still running. The comment lives on the fields in `vite.config.ts` where someone editing them will see it, and `release.yml` greps the built block for both, because a comment is not a gate. The download URL, the match list and the description are all free to change; those two are not.
- **`API_MINOR` moves on the first additive merge after the current one has SHIPPED IN A RELEASE TAG, and every additive merge before that release rides it.** The older wording was one bump per merge to main, which does not distinguish a merge from a release, and two separate changes have now had to reach for the answer. A minor is a claim about a surface a player can actually install, and it has exactly two observable consequences: `runtime/supervisor.ts` refuses an addon whose declared minor exceeds what the loader implements, and `host/updates.ts` keeps that addon out of the update list. Both compare against a loader somebody is RUNNING, and the only artifact is the release asset. So while no tag contains the current number, no addon anywhere can be running against a loader that claims it, the failure a fresh bump would prevent cannot occur, and bumping again would assert that a distinct targetable surface existed when nothing an author can install ever implemented it. Check with `git tag --contains <the commit that set it>`: empty means keep riding. A member changing SHAPE or leaving still moves `API_VERSION` instead, whatever the release state.
- **The git tag is the only source of a release version.** `package.json` stays at `0.0.0` in the tree on purpose and `vite.config.ts` deliberately does not set `userscript.version`, so vite-plugin-monkey falls back to it. `release.yml` runs `pnpm pkg set version` from `${GITHUB_REF_NAME#v}` before building and then greps `@version` out of BOTH built files to prove the stamp took. Keeping a version in the tree as well would be a second place it can disagree from, and the disagreement is silent in the worst way: a manager comparing an asset that claims the wrong version either never updates or reads a release as a downgrade. A local `pnpm build` therefore reports `0.0.0`, which is exactly what an unreleased build is.
- **There is ONE canonical artifact and nothing may host a copy.** The GitHub Release asset, reached through the `releases/latest/download` redirect. `loader/dist/` is ignored and is never committed, on a tag or otherwise. The scheme this replaced pointed `@downloadURL` and `@updateURL` at `raw.githubusercontent.com` on `HEAD` for a path `.gitignore` excludes, so it was a 404 that nothing reports: a player whose update URL 404s gets no error, no badge, and no updates ever. `@updateURL` points at `woc-loader.meta.js`, the metadata block alone, so an update check is 1.6 kB rather than 486 kB. Both files are built in one run and attached together, or a version check answers about a build nobody shipped.
- **A published release is immutable.** A defect found after publication is a new patch tag, never a re-upload: a replaced asset under one tag means two different files claiming one version, and every checksum, cache and mirror that saw the first one is now wrong with nothing to indicate it. Deleting a release is acceptable within minutes and before anyone could have installed; after that it is a patch.
- **`CHANGELOG.md` is generated from commit titles, and the VERB is the category.** Never hand-edit it. This works because of a convention this file already imposes for readability: a title is a capitalized imperative verb phrase with no type prefix. `Add the net and world read surfaces` is an addition and `Build the runtime bundle before linting` is a change, and neither needed a `feat:` in front of it to say so, so `cliff.toml` groups on the verb rather than on a prefix. The practical consequence when writing a commit is that the catch-all files anything unrecognised under Changed, so a title that buries its verb ("Support for X") is categorised correctly by accident at best: lead with the verb. `tag_pattern` restricts git-cliff to `v[0-9]*`, or a `types-v*` tag would end a loader release section and take its commits with it.
- **A stage scenario states what was ALREADY TRUE in `world`, and what then HAPPENED in `run`, and the split is not stylistic.** `world` runs before the addon body is evaluated; `run` runs after it has mounted and drawn. An addon reads the world on its first line, so a fact stated late is one it reacted to rather than one it started from, and those are different pictures. It usually still looks right, which is what makes the exception expensive. The worked example, found the day the stage was written: `cooldown-bars` draws one bar per running cooldown and asks for the ability's icon while building it, and skill art is filed under the player's CLASS. The scenario set `templateId` after mounting, so the one cooldown the shared fixture already carried got a row built before there was a class to file it under, drew with no icon, and was never redrawn, while the four rows added afterwards all had one. On screen that is `aimed_shot` blank next to `twinstrike` illustrated, which is the exact inverse of the truth (the game ships art for the first and not the second) and reads unmistakably as a bug in `icon.ability`. It cost a probe against the live manifest to establish that the loader was right and the fixture was written in the wrong order. **The rule, not the incident: anything a session would have at login goes in `world`.** The class, the spellbook, the bags, the party. When in doubt, `world`.
- **The stage starts from an EMPTIED player, and the emptying is deliberate.** `liveEntity()` carries `cooldowns: new Map([['aimed_shot', 4]])` because a suite wants a non-empty collection to assert against. In a photograph that is a lie: every addon reading cooldowns would draw a row for an ability its scenario never mentioned, including addons whose subject is something else entirely, and it would be in the corner of their Browse thumbnail forever. `createPlayer` in `stage/src/stage.ts` clears the dynamic collections there rather than changing the shared fixture, because a suite asserting on that Map is asserting on something real.
- **The loader inherits the game's look through TWO channels, and a stage that copies only the first renders a frame with no edge.** The obvious one is `var()`: every rule in `runtime/ui/styles/` is scoped to a loader-owned element (`loader/build-runtime.mjs` fails the build otherwise), so the palette, the faces and the radii all arrive as tokens. The one that is easy to miss is that the kit deliberately WEARS three game classes: `panel` on a frame, a tooltip, a modal and a menu, `panel-title` on a title bar, and `x-btn` on a close button, so those surfaces inherit the game's own border, background, shadow and title face instead of keeping a copy that would drift. **`.panel` is where a frame's 2px border, its outline and its three shadows live**, so tokens alone do not reproduce one: with the tokens and without the rule, every colour on a frame is right and the frame has no edge at all. That shipped, and it was found by looking at the stage and asking why the combat meter had no frame. `pnpm theme` takes both now, each rule wrapped back in the at-rules it was found in: the LAYER keeps the loader's unlayered sheet outranking the game exactly as it does in the real thing, and the MEDIA query keeps a `forced-colors` override that replaces the border out of an ordinary screenshot. `tools/kit-classes.ts` reads the kit and `tests/tools-theme.test.ts` fails when it wears a class the extractor does not know about, because the failure is otherwise silent.
- **A preview is CROPPED to what was drawn, and the scale is chosen so it fills the slot.** Placement is therefore not a thing a scenario has to arrange: `pnpm shots` takes the union of every `.woc-addon-frame` rect plus 24px for the panel's `0 2px 16px` shadow, so where a frame sits in the viewport never reaches the file. What it cannot fix is SHAPE. `ui.frame` floors a frame at the size it opened at (`sizeBounds` defaults `min` to the declared size), so a seeded box SHORTER than the addon's own `height` is silently clamped back up: `combat-meter` opens at a fixed 320px and a scenario asking for 232 gets 320 with no warning. The fix for a half-empty panel is therefore to give the scenario more content, never a smaller box. The scale comes from `MIN_DEVICE_WIDTH`, which is the site's own card slot, and it is VERIFIED against the capture rather than predicted from it: a frame sized by its content lays out a pixel or two differently at another scale factor, and `cooldown-bars` measured 245 CSS px at 1x then captured 228 at 3x, which is 684 device pixels against a 700 slot. Growing for width and shrinking for the 512 kB cap are two separate passes in that order, because run together they oscillate.
- **A preview may be a SHEET of several scenarios, and every panel is its own iframe.** An addon whose LAYOUT is a setting has two pictures worth taking and a Browse row with space for one: `cooldown-bars` draws either a column of bars or a strip of swept icons, and which one ships should not be a coin toss. So several scenarios may carry `preview: true`, and they are drawn left to right in array order with a `caption` under each. Mounting one addon twice in ONE document breaks three ways at once, which is what the iframes are for: two elements carrying `#woc-addons`, two registrations of the same keybind fighting over it, and one fqid meaning one storage namespace and one bus identity. Same-origin panes cost nothing and compose the readiness contract for free, since each reaches its own `data-stage="ready"` and that already means its fonts and icons are done. Captions are drawn in the PAGE rather than composited afterwards: sharp renders text through librsvg against installed system fonts, and Cinzel is not one. **The margin is applied once, per pane, and the sheet crops exactly**: each pane leaves 24px around its own frames for the panel shadow, so a second margin at the outer edge put the panels adrift in the middle of the first sheet. The one place that does need stating separately is the sheet's `padding-bottom`, because the caption is the last thing in the picture and has nothing under it.
- **`pnpm shots` refuses to guess three things, and the third is the one worth defending.** WHICH scenario is an explicit `preview: true`, because position deciding is invisible and `idle` is first in more than one file. WHEN the panel is done is `data-stage="ready"`, written by the page once the scenario's own `run` has resolved, because scenarios take genuinely different times and a sleep long enough for the slowest still fails as a plausible photograph of a half-drawn panel. And WHAT THE PICTURE SHOWS is never generated: `alt` is written on the scenario, beside the fixture that produces it, and copied into the manifest verbatim. It is the sentence a screen reader reads instead of the image, and inventing one is worse than having none, which is why `pnpm validate` only checks a preview somebody declared.
- **The stage shows the game's DEFAULT theme and can only ever show that.** The game has a theme picker, and `src/ui/theme.ts` rewrites a fixed subset of these tokens on `documentElement` at run time, in JavaScript. Those alternate values are in no stylesheet and cannot be read from one.
- **An addon that needs game CONTENT ships it as a committed table, and the generator that writes it takes the same `--game` contract `pnpm aura-kinds` does.** Zone layouts, gather nodes, rare spawns and quest text are in the game's own bundle and nothing serves them, so the only alternatives to a table are to hand-type one or to do without. The file is a `.json` beside `main.js`, declared in the manifest's `data` array, and read back through `woc.data(name)`. **The declaration is what makes the surface refusable**: the argument is checked against the list, so an addon cannot reach a file it did not say it would. `.json` only, because `woc.data` hands back a PARSED value and a declared `.txt` is a file it could only fail on; at most eight files at 512 kB each, the preview's ceiling and for the preview's reason, since the player waits for this during an install they asked for and it then sits in GM storage for as long as the addon does. `DATA_MAX_BYTES` lives in `shared/addon-data.ts` because two trees enforce it, `host/addon-data.ts` at install and `tools/manifests.ts` in CI, and a second copy of the number is the one that drifts. The data is fetched where the BODY is fetched and cached beside it, which is the same reason install caches the body: by the time the row exists there is nothing left for enabling to defer. `addons/*/generate.mjs` is what writes it, and it is a checkout reader rather than a manifest reader, so it inherits every consequence: `--game` is REQUIRED and never defaulted, a missing source file is a failure rather than a warning, and the checkout's version is stamped into the output so a reviewer can see which release the table claims to describe. Six of the sixteen addons carry one. Regenerate rather than hand-edit, exactly as with `marketplace.json`.
- **Never modify the game repository** to make an addon feature easier. Work through the external surfaces (`window.__game`, `/ws`, HUD DOM ids, `/audio/sfx/*`). External-only is the project's whole premise.

## Dependencies

Ask before adding one, and install the **latest** version. Do not pick an older major to dodge a peer conflict; move the related stack forward together (vite, vite-plugin-monkey, and vitest majors track each other).

In use: `playwright` (headless capture for `pnpm shots`, dev only; needs `pnpm exec playwright install chromium` once), `sharp` (the derivatives `pnpm site` builds and the crop `pnpm shots` writes, dev only), `zod` (schemas, host and tools only), `semver` (gameVersion ranges), `comlink` (bridge RPC), `preact` (manager UI only, never exposed to addons), `interactjs` (frame drag and resize), `happy-dom` (DOM tests), `esbuild` (the runtime and stage bundles, called directly from `loader/build-runtime.mjs` and `loader/build-stage.mjs` rather than through vite), `markdown-it` and `shiki` (the site's docs rendering and its code highlighting, dev only), `vite-plugin-monkey` (userscript build), `@types/node` (types only, for `tools/*.ts`), `git-cliff` (changelog generation, dev only, pinned EXACTLY rather than by range so it matches the version `release.yml` pins the action to).

The preact JSX transform is configured in **three** places and they have to agree: `jsx`/`jsxImportSource` in `tsconfig.json`, `jsx`/`jsxImportSource` in `loader/build-runtime.mjs`, and `oxc.jsx` in `vitest.config.ts`. Vitest 4 transforms with oxc, so an `esbuild` key there is accepted and then silently ignored, which shows up as JSX compiling against react.

## Testing

Pure modules in `shared/` and `runtime/disposal.ts` are unit tested. DOM-touching modules opt into happy-dom per file:

```ts
// @vitest-environment happy-dom
```

`addons/dev-harness` is the other half of the suite: an ordinary addon, fetched over the marketplace path and evaluated with only the published `woc` object in scope. `addons/dev-harness/main.test.ts` runs it through the real loader and requires every check to pass, which catches the two failures a unit suite cannot see: a surface that was never wired to the object an addon is handed, and an addon written against an API that has since moved. It found one on the day it was written, and it was real: before world entry `woc.world.entities` was a bare Map shared by every addon, so the published "set, delete, and clear throw" contract did not hold and one addon's write would have landed in what every other addon read.

**An addon's screenshot lives in the addon's directory too, declared by its own manifest.** `preview` is `{ file, alt }` on `addon.json`, the file is a PNG beside `main.js`, and THREE consumers read that one declaration: the manager draws a lazy thumbnail on every Browse row and the full picture on the install confirmation, the site's catalog and landing pages build their own AVIF and WebP from it, and the README links the PNG directly so GitHub renders it. One file, committed once. It replaced an `icon` field that had been in the schema since the first release and was read by nothing, which is the tell: a field with no consumer never collects alt text and never teaches anyone it is missing.

Three things about it are not obvious. The manager loads it as an ordinary cross-origin `<img>` from the page, which works because **the game sets no Content-Security-Policy** and its own source says one is deferred rather than declined, so `manager/preview.tsx` hides the slot on a failed load the way `ui/kit/bar.ts` hides an icon that 404s; if a policy lands, the fallback is to fetch it in the host, where `raw.githubusercontent.com` is already in the `@connect` list. The URL is built in the RUNTIME rather than carried over the bridge, which is the opposite of what update rows do and is not an inconsistency: an update row is computed in the host because comparing versions needs semver, and a marketplace URL needs nothing banned. And previews are deliberately left out of the site's undersize report, because an addon's preview is nearly always a picture of its own fixed-size panel, which cannot be captured wider without zooming the game: the alternative that was tried first is declaring each one's own width as its target, which the comment on `measure` already calls out as a number that can only ever agree with itself.

`pnpm validate` checks the file exists, is a PNG by signature as well as by name, and is under half a megabyte. That ceiling is the one asset budget here a player pays at a moment they did not choose, since the manager loads it inside the running game.

**An addon's suite lives in the addon's directory, as `main.test.ts`.** `tests/` is about the LOADER; a suite about one addon belongs beside the file it runs, and it travels with the directory a third-party marketplace would copy. Three things had to move for that to be true rather than merely tidy, and all three are the point: `vitest.config.ts` includes `addons/*/*.test.ts`, `tsconfig.json` includes the same glob so `tsc --noEmit` still typechecks it (the directory was EXCLUDED before, so a colocated test would have compiled against nothing and nobody would have noticed), and the `tests/**` block in `biome.json` names the glob too and sits after the `addons/**` one so the test relaxations win. `tests/addons-suites.test.ts` fails if any addon directory has no suite, because the failure it catches is a green run with one fewer file in it rather than a red one.

Start from `tests/fakes/addon.ts`. `mountAddon` parses the REAL `addon.json` through the schema CI uses, seeds settings BEFORE evaluating (the loader hydrates and then runs the body, and an addon reads `woc.settings` while building its first frame), and returns one `dispose` covering both the addon and the shared services. Everything an addon suite adds on top is the fake world that addon needs.

**Anything that touches the game's wire or its live state is verified by hand against a running PBE client before it is called done.** Mocking those would test the mock, and the failures they produce are silent: a field read at the wrong nesting level, or under the wire's name instead of the entity's, simply never matches and never complains. Build a throwaway userscript that imports the real modules, run it against a live session, and turn what it observed into a fixture. That is how the bootstrap handshake, the `__game` probe, the socket hook, and the `world.on` signatures were each checked.

Write tests that fail on regression, not tests that restate the implementation. When fixing a bug, add the failing test first.

## Style

The mechanical rules are in [STYLE.md](STYLE.md), which is the one to read before writing code. What follows is the part that is this project's taste rather than the linter's.

- TypeScript strict, ESM, explicit `.ts` extensions on relative imports.
- Private declarations come first in a file, the exported surface last. `useExportsLast` enforces it.
- Module size is a design constraint, not a cleanup task: 50 lines per function body and 300 per file. A factory that outgrows 50 lines is usually holding two concerns; split it while writing it rather than when the linter says so.
- Markdown is not hard-wrapped. One line per paragraph or bullet, however long.
- No em dashes, en dashes, or emoji anywhere: code, comments, docs, or commits. Use commas, colons, parentheses, or "to" for ranges.
- Commit titles are a capitalized imperative verb phrase, with no type prefix, no scope parentheses, and no colon: `Scaffold the addon loader workspace`, not `chore(loader): scaffold workspace`. Every commit carries a body explaining what changed and why.
- Comments explain intent and non-obvious constraints, not what the code says. No separator comments; if a file needs sections, split it.

## Development target

Develop against `https://pbe.worldofclaudecraft.com` or `pbe2`. PBE USUALLY runs ahead of live, so game drift shows up there first and the per-host probe gets exercised by real change rather than staying speculative.

**"Ahead" is the wrong model, and a version string is not the answer.** The two channels DIVERGE IN BOTH DIRECTIONS, and the version they report says nothing useful about which content each carries. Measured 2026-08-04, when live reported v0.34.0 and pbe reported v0.33.0: the hunter skill manifest carried 25 ids on live and 32 on pbe, with EIGHT live-only (`wyvern_sting`, `multi_shot`, `deterrence` among them) and FIFTEEN pbe-only. So the channel reporting the OLDER version was simultaneously missing content live had and serving content live did not. This is the same divergence the `pnpm icons` rule already refuses to union, restated as an operational hazard: neither channel is a superset, and a version comparison cannot tell you which way a given id falls.

What follows from it. Every by-hand generator that writes a COMMITTED artifact reads LIVE by default and takes `--host` to go elsewhere: `pnpm cues`, `pnpm icons`, `pnpm items`, `pnpm theme` and `pnpm shots`. The reason is not that live leads, because it does not; it is that a committed artifact describes what a PLAYER is running, and players are on live. `pnpm stage` and `pnpm dev` keep pbe, because a person watching an addon react to an unshipped game wants the drift.

**A STAGE FIXTURE must use ids present on BOTH channels, and this is the rule that is easy to miss.** A preview is one committed file with nothing in it recording which channel it came from, so a fixture naming a live-only id photographs with art from live and without it from pbe, silently, and the alt text describing that row is then true or false depending on who ran the capture. `cooldown-bars` shipped a `wyvern_sting` row for exactly one capture before this was measured; it is `rapid_fire` now, which both channels serve. Check an id on both before putting it in a fixture.

Two artifacts already carried the cost of getting this wrong. `stage/theme.generated.css` had been generated from pbe and carried a `--color-ruin-*` token family that exists in no game tag at all, so it came from a pbe branch that was abandoned rather than released. And the `cooldown-bars` preview showed `counter_shot` art that live had not yet shipped, so for a stretch the committed picture showed players something their own game did not draw. A capture taken from the wrong channel is not a failure; it is a plausible picture of a game nobody is running.
