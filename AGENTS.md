# AGENTS.md

Working instructions for this repository. `CLAUDE.md` points here; this file is the single source of truth.

## What this is

A userscript addon platform for the browser game World of ClaudeCraft, plus the official addon marketplace. It is **fully external to the game**: no game source is modified and no build is forked.

Tampermonkey and Violentmonkey are first-class. Greasemonkey 4 is best-effort: it has no value-change listener, so cross-tab sync there runs over a BroadcastChannel fallback.

The loader has two halves in different JavaScript realms. The **host** runs in the userscript sandbox and owns GM storage, marketplace fetching, and the registry. The **runtime** is injected into the page realm and owns `window.__game`, the WebSocket hook, DOM, keybinds, audio, and the addon API. They talk over a Comlink-wrapped `MessageChannel`, and only storage, addon source, and registry state cross that boundary.

## Setup

```sh
corepack enable        # pins pnpm from package.json packageManager
pnpm install
```

Node 24 (`.nvmrc`). The tools import `.ts` modules directly and rely on Node's built-in type stripping, which is why every relative import carries an explicit `.ts` extension.

**`stage` is written `pnpm run stage` throughout this file because the short form does not run it, and the `run` must not be tidied back out.** pnpm owns `stage` as a subcommand of its own, so `pnpm stage veinsight` answers `ERR_PNPM_STAGE_UNKNOWN_SUBCOMMAND` and a bare `pnpm stage` answers `ERR_PNPM_STAGE_SUBCOMMAND_REQUIRED`. It does not fall through to the script, and the error names pnpm's own subcommands rather than anything here, so it reads as a broken install rather than a wrong invocation. Only `stage` is affected: against pnpm 11.8's full command list the only other collision is `test`, and that one is benign because pnpm's builtin is an alias for `run test` and forwards arguments. Check `pnpm help -a` before adding a script.

**Formatting is Biome, not Prettier.** Run `pnpm fix` rather than fixing style by hand. Config is `biome.json`: 2-space, `lineWidth` 100, single quotes, semicolons, trailing commas.

**`pnpm fix` and `pnpm lint` both take paths, and scoping them matters whenever more than one thing is editing the tree**, where a whole-tree write can land on a file something else is halfway through saving. Biome with no path defaults to the tree, so the bare form is unchanged.

**`pnpm test` takes paths as well, and the reason to scope it is that write rather than the clock.** The whole gate runs in well under a minute, so subsetting it to save time buys nothing, and a subset chosen wrongly hides the break it was chosen around. Scope while writing one module (`pnpm exec vitest run addons/<id>` beside `pnpm lint <path>` and `pnpm check:ts`), and run the gate whole before calling anything done.

**The same concurrency cuts the other way for READING the tree: a full-tree test run is not atomic, so a red result taken while anything else is working has to be re-run before it is reported.** Vitest reads every suite in the tree, and a module saved halfway through means some files were read before the edit and some after, which presents as a cross-boundary break rather than as a race. **Both failure modes cost something and the second is the expensive one:** first an agent is sent to debug a file that was already correct, and later, once everyone has learned that reds are sometimes phantom, a GENUINE break is waved away as probably another mid-write. Re-run, and if it is real it is real twice. Same shape as `pnpm shots` above, which bundles 16 scenario files and rewrites 16 manifests: a shared tree read while it moves.

A bare `pnpm index` stamps `generated` with the current time, so it produces a one-line diff even when no addon changed. That is expected; CI stamps from the commit instead, so re-running on the same commit is byte-identical.

## Lint and type strictness

**Read [STYLE.md](STYLE.md) before writing a module.** It lists the rules that actually fire here with the idiom that satisfies each, plus the two places Biome and TypeScript want opposite things. Most of these rules ask for a real split rather than a formatting fix, so discovering them at the end of a change costs a restructuring pass.

The linter runs Biome's **`preset: "all"`**, every rule it ships, with `--error-on-warnings`. The tree is also clean at `--diagnostic-level=info`, and `pnpm lint` FAILS on an info finding: `tools/lint.mjs` reads Biome's JSON summary and treats errors, warnings and infos alike, because `--diagnostic-level` controls what Biome displays rather than what it fails on and most of the rules that bite here report at info. It takes paths, so `pnpm lint <file>` is the fast check while writing one.

**Fix the violation, do not turn off the rule.** Almost everything the strict preset flags has a real fix, and reaching for the config first hides work rather than doing it. `GM_*` interface members are renamed to `legacy*` and mapped at the boundary rather than exempting `useNamingConvention`; `import.meta.dirname` replaces `fileURLToPath` rather than exempting `noNodejsModules`; `export *` becomes explicit named re-exports rather than exempting `noReExportAll`; a long function is split rather than raising a threshold.

Exemptions are last resort and need a stated reason in `biome.json`. The current set is all structural:

| Off | Where | Why it cannot be fixed |
|---|---|---|
| `useQwikValidLexicalScope` | everywhere | Demands closures be wrapped in Qwik's `$()`. There is no Qwik here. |
| `noDefaultExport` | `vite.config.ts`, `vitest.config.ts`, `loader/src/raw.d.ts` | Both tools resolve config only from a default export, and a module declaration for `?raw` imports has nothing but a default to declare. |
| `noNodejsModules`, `noConsole` | `tools/**`, `loader/build-runtime.mjs`, `loader/build-stage.mjs`, `addons/*/generate.mjs` | Node builtins are the purpose and console is the output channel. |
| `noSecrets`, `noMagicNumbers`, `useTopLevelRegex`, `noMisplacedAssertion`, `noExcessiveLinesPerFile` | `tests/**`, `addons/*/*.test.ts`, `addons/*/stage.ts` | Combos like `'Ctrl+Alt+Shift+Meta+KeyD'` trip the entropy heuristic and literal values are the fixtures; `.toThrow(/message/)` is the natural assertion; an assertion inside a shared helper is the point of the helper; and a suite is one subject per file, which splitting by line count would scatter. |
| `noExcessiveLinesPerFile` | `**/*.generated.d.ts` | A generated union is one name per line and its LENGTH IS CONTENT: the skill-icon union is 327 names across nine classes, in a 365-line file. The only ways under 300 lines are to drop names or to put several on a line, and the second destroys the reason for the format, which is that art landing or moving shows as a one-line diff. |
| `noExcessiveLinesPerFile`, `noHexColors` | `**/*.generated.css` | `stage/theme.generated.css` is a TRANSCRIPTION of a deployed game's own rules, so rewriting a colour into another notation would make it no longer the thing it claims to be, and a diff against the next reading would show every touched line as a change. |
| `noExcessiveLinesPerFile` | `addons/**` | An addon is one file BY DEFINITION: the manifest names a single `entry` and the loader evaluates it with `new Function`. There is nothing to split into. |
| `noReactSpecificProps`, `noSolidDestructuredProps`, `noJsxPropsBind`, `useSolidForComponent` | `**/*.tsx` | The Solid rule family, and there is no Solid here. `noReactSpecificProps` wants `class` where `noUnknownAttribute` wants `className`, so under `preset: "all"` the two contradict on the same attribute; the rest encode Solid's reactivity model, which preact does not share. The React-family rules stay on, so JSX is still linted. |

Configured rather than disabled: `useNamingConvention` runs with `strictCase: false`, since `URL` and `ID` are ordinary JS naming and vite-plugin-monkey's `downloadURL` is not ours to rename; `noExcessiveLinesPerFunction` allows 200 lines in `tests/**`, since a suite is a file's worth of cases rather than a function body. That test block sits AFTER the `addons/**` one in `biome.json` and has to stay there: a later override wins per rule, so an addon's own suite picks up the test relaxations rather than only the addon ones.

The standard for adding to that table is that the rule is IMPOSSIBLE to satisfy in that location, not that satisfying it is inconvenient. "I would have to restructure this" is the rule working.

When a suppression really is right at one site, use an inline `biome-ignore` naming the rule and giving a reason that says why the CODE is right. An unused suppression is itself an error (`suppressions/unused`), so a speculative one fails the check: `new Function` is not flagged by `noGlobalEval` in Biome 2.5.5.

TypeScript runs `strict` plus `noUncheckedIndexedAccess`, `noImplicitOverride`, `noFallthroughCasesInSwitch`, `noImplicitReturns`, `noUnusedLocals`, `noUnusedParameters`, `noPropertyAccessFromIndexSignature`, `exactOptionalPropertyTypes`, `allowUnreachableCode: false`, and `allowUnusedLabels: false`.

## Rules that are load-bearing

### The two realms, the bridge and the bundle

- **zod must never reach the runtime bundle, and neither must semver.** `loader/src/shared/schema.ts` is the only zod dependant and `shared/gameversion.ts` and `shared/version.ts` are the only semver ones. The runtime imports their types with `import type`, which `verbatimModuleSyntax` erases; `loader/build-runtime.mjs` fails the build if either resolves there. **A runtime module that needs a CONSTANT the schema also uses gets its own module for that constant**, which is why `API_VERSION` and `PERMISSIONS` live alone in `shared/api-version.ts` and `shared/permissions.ts`: a value import of anything in a zod module drags the library and its fifty locale files, and a type import costs nothing. The same reasoning is why update rows are computed in the host and carried over the bridge rather than derived in the manager: the comparison needs semver, and a hand-rolled one fails silently, since `1.10.0` sorts before `1.9.0` as a string.
- **Neither a host module nor a Node module may reach the runtime bundle.** The GM globals and `@types/node` are both declared ambient project-wide, for the sandbox half and for `tools/*.ts`, which removes the compiler's protection against the page half doing the same: `readFileSync` in a runtime module typechecks. `loader/build-runtime.mjs` inspects the esbuild module graph and fails on any input under `loader/src/host/` and on any `node:` or bare builtin import. Shared code goes in `loader/src/shared/`. The same ambience is why `runtime/dom-timers.ts` exists: `setTimeout` returns a `Timeout` under Node's types and a number in a browser, and the runtime only ever runs in a browser.
- **`host/globals.ts` is the only module that names a GM function.** Everything else goes through `host/gm.ts`, which feature-detects on the shape `readGmSource()` returns. The ambient tampermonkey types declare the full surface, so they say nothing about what a given manager ships: a direct call is what breaks Greasemonkey, and the failure only shows up on a browser nobody tested.
- **Nothing but the handshake touches the `window` message channel.** Both halves drop their window listener the moment the port is transferred, and everything after that is on the port. A listener left behind would hand a second port to anything that replays the hello.
- **The runtime ships without a source map.** Inline is the only form that could work, since the host injects the bundle as `<script>` textContent and an external `.map` has no URL to resolve against, but that is a reason it must be inline rather than a reason to have it: it is 8x the bundle (149 kB to 1.18 MB) and the host re-injects the whole string on every page load. `pnpm build:runtime:debug` turns it on, reading the flag from `argv` and never `process.env`, which this script deliberately has no dependency on.
- **Anything that returns a promise rejects rather than throwing.** Comlink turns a synchronous throw into a rejection, so the bridge hides the difference and a direct caller does not. The manager holds the registry directly when it can, so a `pending()` stub that throws is a real failure mode the bridge tests cannot see.

### Reading the game

- **The world types are a CLAIM about the game, and the loader checks what it can.** `runtime/world/game-types.ts` describes shapes in a repository this one does not depend on, must never depend on, and cannot compile against, so every read in `world/backend.ts` is an assertion rather than a derivation. `world/shape.ts` walks the live player once when the world goes live and reports every field that is missing or of the wrong kind. `tests/types-parity.test.ts` proves only that the loader and the published package agree with EACH OTHER, and they could be wrong about the game together.

  **A commit that adds an API SURFACE adds its own parity pair to that file.** A facet with no assertion is not a failing test, it is silence, which is how `bus` went uncovered from the day it landed. **The one-line backstop does not close this:** `wocSatisfiesPublished` compares the whole `WocApi` against the published one and so reaches every ROOT member (thirteen of them, `settings`, `onDispose`, `onFrame`, the timers and the log functions among them), but a new FACET is reached only through its own type. A new surface owes three lines: the pair in both directions, plus a `wocCarries*` against `WocApi['<facet>']`, because the pair compares two DECLARATIONS and the third compares what the assembly hands over.

  **Both directions, and a two-way pair is weaker than it looks.** Dropping a field from one side leaves the other a SUPERSET, which is still assignable, so only ONE direction fails. `SameFields` compares key sets, and it is the only thing that catches a field added to one side alone when that field is OPTIONAL, which is how every field the game has added to an existing event has arrived. **The gate is `tsc --noEmit`, never the runner:** these are type-level assertions and oxc strips types, so a mutation that errors on three lines of that file leaves `pnpm exec vitest run` all green. Verifying one means reading the typecheck and mapping its line numbers back to the const names.

  **A direction that is FALSE is not automatically drift, and forcing it is the wrong repair.** `PaintOpts.frame` is a `PaintFrame`, `{ visible: boolean }`, because that is all a repaint reads, while the package publishes the whole `Frame` because that is what an addon holds. The loader accepts strictly more than the package promises, every published-legal call works, and asserting the reverse would demand the loader stop accepting what it deliberately accepts. Pin the direction that fails when the package promises something the loader cannot honour, and say in the comment why the other is absent.
- **A field is published only if it was found ON THE WIRE, and the shape check cannot enforce that.** The online client builds every entity with defaults and fills in what the snapshot carried, so a field the server never sends is present, of the right kind, and holds that default for the whole session; `checkEntityShape` passes it. Reading `inCombat` to decide a fight is over concludes that every fight has ended, and resets on every hit. `abilityCharges[id].maxCharges` is the same trap one level down and is deliberately NOT published: the server keeps the maximum to itself and the client zero-fills it. Verify against `wireEntity`/`identityFields`/`dynamicFields` and the self payload in the game's `server/game.ts`, not against `src/sim/types.ts`. **Those are not two places to check:** `selfWireJson` SEEDS from `wireEntity` and then assigns the self-only stats over it, deleting nothing, so the self payload is every entity field PLUS the extras. **Read the function, do not grep it**, because a payload assembled by spreading does not mention its inherited fields anywhere a search can reach. Currently NOT on the wire, and therefore not published: `inCombat`, `moveSpeed`, `onGround`, `jumping`, `stealthed`, `offhandWeapon`, `meleeHaste`, `rangedHaste`, `ccDr`, `ccDurationReduction`, `jailed`. **`jailed` is the cheapest possible demonstration that the list is about SEND SITES and not about how a field is declared**: it is declared four lines from `cheaterMark` in `src/sim/types.ts`, in the same words (server-set, never true offline, never user-settable), and `identityFields` emits one as `chm` and says nothing about the other, so a reader reasoning from the declarations publishes a flag that is false about every jailed player in the game. **The last two are the entry to read when the list looks like a list of small things**: they are the crowd-control diminishing-returns ladder and the item-set reduction over it, so game 0.37.1 could rework every PvP DR rule in the game (stuns exempted from the ladder, fear moved from absolute seconds to a multiplier over the ability's own duration) with nothing an addon could read either before or after. The client constructs `ccDr` as an empty Map (`src/net/online.ts:1358`), so a DR display is something an addon TRACKS from the applications it can see, and `site/content/docs/patterns.md` is where that is said to authors. **`cheaterMark` is the newest field to have gone the other way and never appeared here:** game 0.38.0 added it and `identityFields` emitted it in the same release (`server/game.ts:1446`, decoded at `src/net/online.ts:3051`), so it was publishable the day it landed. **`castTargetId` was on that list until game 0.36.0 and is published now**, which is the list working rather than a correction to it: `dynamicFields` began emitting it as `castTgt`, inside the `castingAbility` guard, so absence means "not casting, or casting something untargeted" rather than "no target". A field leaving this list is a normal event; check the send site before assuming any entry is still true. Self-record-only fields are published and marked as such. **`savedMana` is the newest arrival and it is the OTHER shape of this rule, a field that was declared for releases and started being sent in one:** it has sat in `src/sim/types.ts` since well before 0.38.2 with nothing emitting it, and game 0.39.0 added `if (p.resourceType !== 'mana' && p.savedMana > 0) self.sm = wireParkedMana(p.savedMana)` (`server/game.ts:8957`), on the object `JSON.stringify`'d into the self payload one line down, decoded unconditionally at `src/net/online.ts:3347`. So nothing about the DECLARATION changed in the release that made it publishable, which is the whole reason this list is kept against send sites: a reader diffing `src/sim/types.ts` between the two tags sees nothing at all. It is a druid's real mana pool, parked while a form runs the live bar on rage or energy, floored by `wireParkedMana` and omitted at rest, so "no form" and "a form with an empty parked pool" both arrive as 0. **Read the SEND SITE, not only the wire**, because a `maybe()` field is delta-guarded and does not appear in every snapshot, so one live session mid-fight can show a field that is genuinely sent looking exactly like a field that never is: `stats` and `weapon` both ride the self payload (`maybe('stats', p.stats)`, `maybe('weapon', p.weapon)`) and are published. **And then check that the send site is a send.** `inCombat`, `moveSpeed` and `onGround` are all read in `captureBotDetectionSnapshot` (`server/game.ts:3467` at game 0.39.0, and the line moves every release, so re-find it by name), a server-internal record that never becomes a frame, so a grep finds a server write that reads exactly like a send; `dynamicFields` writes `out.rp` at `server/game.ts:1410`, so `rangedPower` rides every entity record including your own. The question is never whether the field name appears in the server, it is whether the object that write lands on gets serialized into a frame. **Re-read at game 0.40.1 and the list did not move in either direction**, which is a result rather than an absence of one: nothing left it and nothing joined it. The one reading that looks like a change and is not is `inCombat`, which `server/game.ts` does send, as `inCombat: e.inCombat ? 1 : 0` on a PARTY FRAME member record; it has been sent there since before 0.39.0, it is already published as `PartyMember.inCombat`, and `world.combat` is derived from it. It is on this list because the list is about the ENTITY record, where it is still never sent. A field can be a lie on one surface and the truth on another, which is the same rule `publicInstanceView` states for items.

  **`Entity.targetId` is the case this rule catches on a field ALREADY PUBLISHED, and only a live session can see it.** It is emitted as `tgt` for players and bots only; a mob's selected target rides `aggro`, from `aggroTargetId`. So on every mob `targetId` is present, correctly typed, written by nobody, and permanently null, and a target-of-target display built on it works on players and is blank on everything it is actually pointed at. Both fields are published and `packages/types/entity.d.ts` says which is which; `world.unit('targettarget')` hides the difference, and hiding it is most of what that resolver is for.
- **A CORPSE STOPS BEING LOOTABLE BEFORE IT STOPS BEING AN ENTITY, and nothing about the entity says so except one flag.** Game 0.40.1 added a corpse-decay rule: once a dead mob's loot window elapses, `corpseLootAvailability` (`src/game/corpse_loot_availability.ts`) returns before it looks at the tap lock at all, so nobody can open it whatever their rights, and `entity_view_policy_core.ts` drops it from the game's own render and pick view. What it does NOT do is clear anything: the entity keeps `lootable`, keeps its whole `loot` record, and stays in `world.entities`. The game's own guards read `!mob.loot || corpseHasDecayed(...)` rather than relying on the record going away, which is the proof that it does not. So a loot display that mirrors only the rights rule goes on offering slots off a body the player cannot see and cannot open. `world.corpseLoot()` mirrors the decay arm too and publishes it as `CorpseView.decayed`.

  **The flag it is derived from is a sentinel with a countdown's name, which is why `corpseTimer` is read and not published.** It is sent as the sparse `cd` (`server/game.ts:1475`, mobs only) and the client expands it back to 0 or 1 (`src/net/online.ts:3165`), so online it never holds a duration; the offline sim carries the real countdown. That is the `lootFfaTimer` shape exactly, and it gets the same treatment: read internally, published as the boolean it actually answers. The one place the loader deliberately DISAGREES with the game is the unreadable case. The client initialises `corpseTimer` to 0, which reads as decayed, so a defaulted reading would blank a live corpse's loot; the loader defaults to the window being OPEN, which leaves the display exactly as it was before this rule existed.

- **Read the wire from the wire, not from the declarations.** They disagree silently and both directions have bitten: the input ack rides `snap.self`, not the snapshot head, and an Entity carries `maxHp`/`resource` where the snapshot that delivered it said `mhp`/`res`. Reading the wrong one finds nothing, raises nothing, and looks exactly like a value that never changes. `tests/fakes/frames.ts` holds shapes captured from a live client; add to it from a real session rather than from `src/sim/types.ts`.
- **A fake must be the same KIND of thing the game hands over, not merely the same shape.** `__game.input.keybinds` is a class instance whose matchers read `this`, and a fake built from arrow functions closing over local Maps has no `this` to lose; such a fake passes the whole suite while the loader throws on the first real conflict lookup and blanks the manager pane, because the manager reads conflicts during render. `tests/fakes/game-keybinds.ts` is a class for that reason. Anything reached through a game object is also called defensively: a future update can leave something callable in place that throws when called, and the cost of that has to be a missing warning rather than a dead screen. **A generated DEFAULT is the quieter version of the same mistake, valid for the type and wrong for the domain.** `defaultFor` in `tests/fakes/entity.ts` answers 0 for every `kind: 'number'` field and ignores `nullable`, so `ownerId`, which is `number | null` and means "nobody" as null, comes back as 0 on every fixture entity including the player, and an implementation resolving a source through `ownerId` computes the player's own principal as 0 and matches nothing against a fixture that is green everywhere else. The fixture is the thing to fix, not the addon.
- **Nothing in the game's HUD exists until world entry.** `#ui`, `#options-menu`, the micro-button rail and everything in it ship inside `<template id="game-ui-template">` and are cloned into `document.body` only when the player enters the world; `#game-version` is the sole anchor outside it. A one-time lookup at DOMContentLoaded finds none of them and fails silently. Injections wait through `ui/hud-mount.ts`, on a `childList`-only observer: the clone is one fragment insert of direct body children, and a subtree observer would run a selector against every HUD mutation for the rest of the session. Reading `index.html` for this is a trap, since grepping an id shows the element but not the `<template>` that encloses it.
- **Every game selector goes in `runtime/ui/anchors.ts`.** They are the external surface the whole project rests on and the game owes us nothing for any of them, so a game update that moves one has to be a single edit. The manager's Diagnostics pane resolves the table live, which is what makes drift visible before an addon author reports it as a bug.
- **Skill art has a SERVED manifest.** `/ui/skills/<class>/mapping.json` lists which ability ids ship a painted `.webp`: nine files, one per class, with no index over them, so the class list is written out in `tools/icons-core.ts`. It is written out rather than discovered for a second reason since game 0.39.0, which is that the directory count and the class count have come apart: there are TEN folders there now and the tenth is `pet`, which is not a class and must not be read as one (see the pet-ability rule below). `pnpm icons` renders them into `packages/types/icons.generated.d.ts` and `runtime/ui/kit/skill-art.ts` reads one per class at run time, the same split `pnpm cues` and the sound engine make over the cue pack. Every OTHER ability's icon is composited on a canvas by a module that is not on `__game`, so it exists in the game and has no URL an addon can point at. The reason to read the manifest is not the requests it saves but the ambiguity it removes: without it a blank icon slot means either "no file exists" or "the loader built the wrong id", and a 404 cannot tell those apart. The manifest carries `{abilityId, sourceFile, output}` and NO display name, so it cannot recover an id from an event's ability field.

  `pnpm icons` reads LIVE by default, because the published types describe what most players are running. **Do not union the channels.** They diverge in BOTH directions, measured across all three on 2026-07-30: pbe carried 318 ids to live's 237, live carried `judgement` that pbe had already dropped, and pbe2 matched live exactly. **The counts are the perishable half and the divergence is the durable one**, so read that reading as dated: live is at 401 as of game 0.36.0, which rebuilt the classes and took paladin from 25 ids to 51. That release also RETIRED five (`judgement`, `divine_shield`, `holy_wrath`, `aura_surge`, `cleansing_verdict`), which is why the per-class counts sit in the generated header: a count going up is art landing and a count going down is art moving, and only the second is worth stopping for. A union would autocomplete names most players' games have no file for. Narrowing costs autocomplete and nothing else, because the RUNTIME reads the manifest from whichever host the player is on and the published union is open where it is used, so a pbe-only ability still resolves there.

  **Game 0.40.1 took it to 393, and it is the first release where the total went DOWN.** Two arrived, both rogue utility poisons (`melting_acid`, `nightshade_coating`), and ten LEFT, all of them warrior: the `sport_*` kit that the deleted Vale Cup minigame owned. The per-class header is what says which of those two things happened, since a net of minus eight says neither: rogue reads 37 to 39 and warrior 73 to 63. The retirement cost nothing to check, and the check is the point rather than the result: the only place in this repository that named a `sport_*` id was the generated union itself, so regenerating retired them and nothing else had to move.

  **The manifest is the answer even when a FILE says otherwise, and game 0.38.0 is the case that proves it.** That release added `public/ui/skills/druid/challenging_roar.webp` and left every one of the nine `mapping.json` files byte-identical, so the art exists, the URL a naive builder would compose is live, and the manifest the runtime reads has never heard of it. Reading the directory would publish an id the game's own resolver does not use; reading the manifest reports 401 at 0.38.2 exactly as it did at 0.36.0, which is the honest count of what an addon can point at. The rule that a blank icon must mean "no file exists" rather than "we built the wrong id" only holds while the manifest is the sole source, so do not reconcile it against a directory listing when the two disagree.
- **Item art has a served manifest too, and its NAME field is provenance rather than the item's name.** `/ui/items/mapping.json` is ONE file rather than a per-class fan-out, so a bag grid of 72 cells costs one request. `pnpm items` renders the id union into `packages/types/items.generated.d.ts` and `runtime/ui/kit/item-art.ts` reads the deployed one at run time, with the same optimistic-until-known contract `skill-art.ts` proves out. The channels are NOT unioned, for the reason the skill manifests are not: measured 2026-08-11, live carried 822 ids and both pbe channels under 700, live being the one AHEAD that week. It carries two lists, `entries` (curated, with a name) and `generatedBatches` (ids only), which do not overlap and whose union is exactly the `.webp` files in the directory. `iconSize` is the shape check, standing in for the `class` field the per-class manifests have: without it a payload that is not this manifest reads as a manifest naming nothing.

  **The name is the ART SOURCE name and drifts from the game's display name.** The game's own gate on the field is that it is non-empty; nothing compares it against the item table, and a content rename rewrites the table and leaves the art provenance alone. Measured against game 0.33.0: 281 of 303 agree and 21 do not. So it is published as `ui.icon.itemArtName`, labelled, and is deliberately NOT generated into the types, because a name that looks authoritative and is sometimes wrong is worse than no name. **It now answers for almost nothing, and the reason to keep distrusting it is unchanged.** Game 0.36.0 moved the catalogue into unnamed generated batches: 307 curated entries became 39, all reagents and bags, and all 38 of those that are items agree with the game today. Nothing GATES that agreement, which is what the rule was ever about, so the ranking below it stands whatever the current count is. **There is no `world.itemName` and there must not be**, because a name API implies a source for one that is right and the item table is bundled into the game's own chunk. **WEAPONS HAVE ART, as of game 0.36.0, and the sentence that used to sit here said they never would.** That release gave every authored weapon a bespoke painting under its own item id and listed it in this manifest, retiring the model-name indirection as far as an addon is concerned. Coverage is now COMPLETE: at 0.36.0 every one of the 837 items ships a file except sixteen, `ITEM_ART_PENDING` is empty, and the manifest's 822 ids are exactly the 822 `.webp` files in the directory. **The sixteen are the one thing the manifest deliberately does not list**, and they are heroic weapon VARIANTS, which ship no file and reuse their base weapon's painting the way they inherit its held model. `runtime/ui/kit/item-art.ts` mirrors that resolution: `heroicVariantId` freezes the id as a pure `heroic_` prefix, all 64 variants in the table satisfy it, and the resolved base is checked against the manifest like any other id, so a URL still means a file exists. `heroic_mark` is the one `heroic_`-prefixed id that is not a variant and it ships its own file, so it never reaches the fallback. **Read the completeness as dated rather than settled.** `itemImageUrl` checks `ITEM_ART_PENDING` first and returns null on a hit, that set held 101 items at 0.33.1, and it refills whenever content lands ahead of its art, so `has()` still has a real false to answer. Game 0.37.1 left the manifest and all 823 files byte-identical, and 0.38.2 left them byte-identical again, which is what "dated" looks like in the quiet direction: a release can move nothing here, twice running, and the way to know is to diff the two tags rather than to regenerate and read a no-op diff as confirmation. Game 0.39.0 moved it by exactly one, `dawnhold_posy`, taking the union to 823 ids; `ITEM_ART_PENDING` is still empty. Game 0.40.1 moved it by six, all of them the tutorial island's (`mother_of_pearl`, `ps_briny_lure`, `ps_castaway_crate`, `ps_ferry_bell`, `ps_lustrous_pearl`, `ps_passing_stone`), taking the union to 829; `ITEM_ART_PENDING` is empty at that tag too, and `src/ui/icons.ts` says so in as many words, that the island's crate and bell icons were rendered from their own world models rather than enumerated as art debt. What that release DID add is a resolution arm ahead of the item ones, `currencyImageUrl` in `staticIconUrl` (`src/ui/icons.ts`), so a currency pseudo-item is answered from `/ui/currency/` before `itemImageUrl` is reached: `icon.item()` does not mirror that arm and answers null for one, which is the honest reading rather than a gap, since no currency id reaches an addon as an item id. The manifest is also NOT a subset of the item table: `backpack` is in it and is not an item at all, the implicit 16-slot bag the bag bar draws first, so anything joining the manifest against items has to tolerate a miss rather than read one as a bug.
- **Aura art has a served manifest as of game 0.39.0, and it is the one that answers a URL rather than a file name.** `/ui/auras/mapping.json` is ONE file, like the item manifest, and `runtime/ui/kit/aura-art.ts` reads the deployed one at run time. Measured on live at 0.39.0 it carries 134 ids in two lists: 129 `assets` entries, `{auraId, output}`, whose file sits under `/ui/auras`, and 5 `externalAssets` entries, `{auraId, runtimeUrl}`, which are auras the game deliberately draws from ANOTHER family's painting (`/ui/delve-affixes/`, `/ui/fiesta/powerups/`) and which carry the finished path. That second list is why the module resolves to a whole URL: composing a path under `/ui/auras` for one of the five would name a file that is not there. `family` is the shape check, standing in for the `class` field the per-class skill manifests carry, and an `externalAssets` value is accepted only as a same-origin absolute path, since it is a URL taken off a document rather than composed here. Re-read on live at 0.40.1 and unchanged in every particular: still served, still `family: 'auras'`, still 129 plus 5.

  **It is the one art reader that is NOT optimistic before its manifest lands, and the ratio is the reason rather than taste.** `item-art.ts` hands back the id first because all but a handful of the game's 823 items ship a file. This family is CLOSED and small and covers the COMPLEMENT of what `icon.ability()` already answers: the game's own resolver (`auraImageUrl`) checks it first and then falls back to the ability art for an aura carrying an ability id, so an aura you cast resolves through `ability()` and never through here. Most ids handed to `icon.aura()` are therefore legitimately not in it, and guessing would spend a request per row to 404 and reach the same blank slot. It answers null until read, and `preloadAuras` is what a caller awaits to make the first row exact. `emberwatch` is the addon that adopted it: it tries the effect's own painting before the caster is looked up, and keeps the mob-portrait fallback, which still carries most of its rows.

- **A cue is not a file.** The game serves `/audio/sfx/runtime-pack.json`, which collapses a numbered family into one cue with variants: measured on live at game 0.40.1, 274 cues, one FEWER than the 275 of 0.38.2 and 0.39.0, and it carries the gain the game normalized each clip to. The one that left is `ui_vcup_kickoff`, retired with the whole Vale Cup minigame at 0.40.1, and it is the first cue this project has watched go: a count going DOWN here means a cue an addon could name has stopped existing, so an addon calling `sound.play` on it now plays nothing. Take cue names and tuning from the pack; a directory listing would offer addon authors the 211 extra file names that resolve to nothing, and would play every cue untuned. The figures are a reading rather than a constant, and the one before this said 432 files and 220 cues; the pack grew under it without the ratio's point changing. `packages/types/cues.generated.d.ts` is that same pack rendered as a union for autocomplete, written by `pnpm cues` and never by hand. It stays an OPEN union (`KnownCue | (string & Record<never, never>)`): the set is content, a game release adds to it before these types catch up, and a published type must not be able to break a working addon.
- **Never modify the game repository** to make an addon feature easier. Work through the external surfaces (`window.__game`, `/ws`, HUD DOM ids, `/audio/sfx/*`). External-only is the project's whole premise.

### Combat records

- **A heal is attributed from `heal2`, never `heal`, and `cueOnly` is ignored by the FLAG.** Only `heal2` carries a `sourceId`; the plain `heal` event has a target and an amount and nothing to attribute it to. `heal2` also emits `cueOnly` records that exist purely to drive a sound and carry no healing, and a meter must skip them on that flag rather than on `amount === 0`, because a genuine direct heal legitimately lands at 0 on a target already at full health.
- **A PET is the player for ATTRIBUTION and is not the player for the ATTACK TABLE, and the two halves are separate decisions.** A pet's records carry the pet's entity id as `sourceId`, and game 0.35.0 resolves each side to its controller before deciding who a combat record reaches, so an owner now receives their own pet's events. Matching `sourceId` against the player's raw id silently drops a hunter's, warlock's or mage's pet damage. **What does NOT follow is resolving a pet to its owner everywhere**: a pet's swing rolls against the PET's hit rating, so folding it into the miss, dodge, parry and block line produces a figure describing neither table, exactly as damage taken is kept out of that line for the same reason. Ask the question AGAINST the player (`ownedByPlayer(id, player)`) rather than resolving both sides to a principal, so a stranger's pet answers no rather than turning the panel into a zone-wide display. **The snapshot is not the only source and must not be the first one.** `damage.sourceOwnerId`, from game 0.36.0, carries the owner as it stood when the record was EMITTED, which closes the one hole the lookup structurally has and closes it at the worst-placed moment available: a pet despawns when its owner dies, so the exchange that killed them is exactly the one whose source has already left `world.entities`. Read the field, fall back to the lookup, and keep asking against the player either way, since a stranger's pet carries an owner id too. A pet row can never draw art, for the reason the id/name rules below give.
- **An ability's ID and its DISPLAY NAME have diverged, and there are exactly THREE exceptions.** `arcane_shot` is shown everywhere in the game as "Fell Shot". Skill art is filed under the ID; combat events carry the NAME. Your own spellbook is the first exception and the only one that works both ways: `world.abilities` closes the join either way. The second is `damage.abilityId`, added in 0.34.0 beside the display-name `ability`: a one-way answer for ONE emit, the primary direct hit. It does reach ANOTHER PLAYER's ability, which `world.abilities.byName` never could, since damage records are world-visible. **Neither of those two reaches a MOB's ability, which is most of what an addon watching a fight sees named.** The gate is a PARAMETER rather than a list of files, which is worth holding because a refactor moves call sites and not gates: every site that fills `abilityId` runs through `runEffects(ctx, p, meta: PlayerMeta, ...)`, the one exported entry point of `combat/effect_dispatch.ts`, or the two paths reached only from it, and a mob has no `PlayerMeta` to enter with. A mob passes a bare display label instead: `'Gravebreaker'` in `encounters/nythraxis.ts`, `spell.name` for a hostile `petSpell`, `null` on a swing. `combat/auto_attack.ts` looks like the counterexample and is not, because the id it passes is set on the player `weaponStrike` path only. **Do not "fix" this by deriving the mapping**, which is still the answer everywhere `abilityId` comes back null. The routes to a real mapping were weighed and rejected: the i18n bundle has all 380 pairs but sits behind a hashed filename discovered from `play.html`, as minified JS, per locale, so it breaks on a bundler change rather than a game change; and correlating a `spellfx` id with the damage that follows is learnable from the wire but a mispairing draws the WRONG icon, which is worse than none. `Aura` is the one shape carrying both, and only for abilities that apply one. Eight addons derive a label from an id as a last resort and all eight still need to.

  **The THIRD exception is `AuraEvent.abilityId`, new in game 0.35.0, and it is the only one that reaches a mob.** `Sim.applyAura` takes an `Entity`, not a `PlayerMeta`, which is why the other two stop at the player. Four limits before building on it. It is filled on the APPLICATION path (a gain, a refresh, and the fade of a same-id aura displaced by a re-brand) plus one stack-bump re-emit in `combat/effect_dispatch.ts`, while roughly thirty other emit sites stay bare, expiries and dispels among them, so a fade usually has no id even where the matching gain did. It covers aura-APPLYING abilities alone, so a mob's swing, plain nuke and DoT tick still carry a label and nothing else. It is an AURA id on the two `applyAura` emits and the CASTING ABILITY's id on the stack bump, which disagree where two abilities share an aura kind (warrior Sunder against rogue Expose), so it is not the uniform promise `heal2.abilityId` makes. And all four fields 0.35.0 added there (`sourceId`, `abilityId`, `stacks`, `refresh`) are optional and must be read as optional. `packages/types/events-combat.d.ts` carries the full note; treat a hit as a bonus and keep the `name` path working.

  **A PET's ability is outside all three exceptions and always will be.** A pet never carries an `abilityId` and its `ability` is either `null` (every melee swing) or a bare template label off `spell.name`; pet abilities are also absent from `world.abilities`, which is the OWNER's spellbook. No icon is recoverable for a pet ability by any route, so name the pet in the tooltip rather than saying "not in your spellbook".

  **Game 0.39.0 added `/ui/skills/pet/mapping.json` and it does NOT refute that, which is worth saying because the path reads exactly as though it does.** A tenth directory appeared under `skills/`, alongside the nine classes, carrying eight ids. They are the game's own PET BAR BUTTONS (`pet_attack`, `pet_growl`, `pet_water_jet`, `pet_feed`, `pet_mend`, `pet_passive`, `pet_defensive`, `pet_aggressive`), and `src/ui/pet_action_icons.ts` opens by saying they are "deliberately NOT ability ids": synthetic action identities, given their own art precisely so the pet bar stopped borrowing a real spell's picture (a hunter's "aggressive" was drawing Rapid Fire). Nothing a pet CASTS is in there, and nothing on the wire ever carries one of these ids, so an addon has no route to obtain one. `pet` is therefore deliberately NOT in `ICON_CLASSES` in `tools/icons-core.ts` and `SkillIconClass` stays at nine: adding it would publish eight names for autocomplete that no combat record, no spellbook and no entity can produce. That is also why `pnpm icons` reports from 9 classes and not 10; at 0.40.1 it reports 393 ids.

  **The same id/name split runs through the game at three levels, and the survivable case is where the label is CARRIED rather than DERIVED.** Items do it (`elderwood_log` is "Highpine Log", `silverleaf_herb` is "Sheenleaf Herb", `thorium_ore` is "Osmium Ore"); mob templates do it too (`webwood_spider` is "Sableweb Lurker", `tunnel_rat` is "Deeprock Digger", both diverged at 0.34.0). What that asks of a generator is one thing: write the game's own label into the table, so a regeneration picks up a rename. A table that had title-cased the id would read "Webwood Spider" forever and no regeneration could fix it. Where a label still has to be derived, disclose it on screen.
- **An event's `ability` is a display NAME, not an ability id, and the `abilityId` beside it is not always there.** Every `damage` and `heal2` emit fills `ability` from `ability.name`, `spell.name`, `abilityName`, or a bare label. `spellfx` puts an id in that field, and `castStart` puts an id OR AN ACTIVITY SENTINEL, a fixed marker naming a timed activity rather than any ability: gathering and fishing were the two, and 0.35.0 took it to seven with the crafting family. THE SET GROWS WITH THE GAME, so match the ones you care about by name and let an unrecognised value fall through as an ability id rather than enumerating them. `CastStartEvent.ability` in `packages/types/events-combat.d.ts` is the ONE declaration listing the current sentinels and every other site points at it; keep it that way. The declared type is `string | null` for both, so nothing says which. **`damage.abilityId` is populated ONLY for the PRIMARY direct hit, and a client must fall back to `school` where it is not set.** Auto-attacks, DoT ticks, and echoed or fanned-out copies (Power Echo, Bladed Echo, Sweeping Strikes) omit it deliberately, so a dedicated impact cue fires once where an ability lands and never replays per tick or per extra target; a hybrid's dot shares the ability's id (Throat Wire's bleed is aura id `garrote`), which is why the tick has to give it up. **Omitted means NULL rather than missing, so a consumer tests the VALUE and not the key.** All seven `damage` emits in `combat/damage.ts` write the field unconditionally, so it rides every record carrying `null` where `dealDamage` was not given one, the evade arm included; contrast `attackAnimationStarted` on those same emits, which is spread in conditionally. The published type is optional as well as nullable, and the optionality is tolerance for a server predating the field rather than a case to expect. `heal2` has carried an `abilityId` for longer and it is a DIFFERENT promise: the applying AURA's id, on a HoT tick and on the application, absent from a direct heal. **An id is otherwise only safe to assume where the field is a map KEY** (`cooldowns`, `abilityCharges`) or where the emit site says `.id`. Where a name has to become an id, slugify it and let the failure be cosmetic: the kit hides a bar's icon slot when the image 404s, so a name that does not round-trip costs an icon rather than a broken row.

### What an addon may do

- **`net` is read-only.** No send API, no synthetic input, no automation. The game's terms prohibit automating play and it runs a bot detector whose heuristics are not public.
- **Never read `localStorage['woc_session']`.** It holds the account bearer token.
- **Outbound frames are redacted before any addon sees them.** The client's first frame on every socket, including every reconnect, carries that bearer token as `{t:'auth-world-N', token, clientSeed}`. `redactOutbound` in `runtime/net/frames.ts` blanks it, matched on the field NAME rather than the frame type so a version bump cannot slip past: game 0.35.0 took `ONLINE_WORLD_LAYOUT_VERSION` from 3 to 5, 0.36.0 took it to 6, adding a `petSpecialWire` field to the same frame, and 0.39.0 took it to 7 for a resource-carrier change that has nothing to do with this frame, and nothing needed touching any of the three times. Anything added to `net.onSend` goes through it. **The redaction is not airtight and the gap is a second route rather than a hole in this one.** The `challengeResponse` frame carries `sig`, `cyrb53(JSON.stringify([nonce, response, seed]))`, a non-cryptographic 53-bit hash, so an addon on `net.onSend` sees `(nonce, response, sig)` triples with `clientSeed` blanked and the seed is in principle recoverable by offline search. No route to the bearer token, which is what the rule above protects. Read it the way the declared-permissions rule reads: an addon cannot take a credential straight off a frame, not that credential material is out of its reach.
- **A tap runs inside the game's own stack.** The socket hook's `send` override is synchronous in the game's call, so every tap is guarded. A throw in loader code must never break the frame the game was sending.
- **Addon source is a function BODY, evaluated in strict mode.** No export, no registration call, `woc` in scope, and a `sourceURL` comment appended so traces name the addon rather than `<anonymous>`. Strict mode is prepended rather than left to the author: a sloppy-mode body turns an undeclared assignment into a property of the page's global object, which is one addon's typo becoming another addon's mystery variable, on a page shared with the game.
- **Shadowed globals are a guardrail and the message says so.** `runtime/shadow.ts` hands each addon proxies for `localStorage`, `sessionStorage`, `indexedDB`, `XMLHttpRequest`, `WebSocket` and `__game` that throw and name the sanctioned API. `document.cookie` is deliberately NOT shadowed: it would mean handing addons a proxied `document`, which breaks every identity comparison in the DOM, and a guardrail that subtly breaks correct DOM code is worse than the gap it closes.
- **Declared permissions are a disclosure, not a boundary, and the pane says so.** Addon code runs in the page realm with the page's globals in scope, so a manifest that declares nothing is not thereby prevented from doing anything. The install confirmation shows the declared list next to that sentence: a permission list with nothing beside it reads as a sandbox, and there is not one.

### The addon API: lifecycle, storage and data

- **Installing an addon enables it, and the registry write is what starts it.** The body is cached at install so enabling is never a network call, which means by the time the row exists the code is already on disk and there is nothing left for a separate enable step to defer. The player has already accepted a confirmation saying to install only what they would trust as a browser extension; not running it is a second decision they did not ask to make. `registry.changed` reaches the supervisor through `runtime/host-events.ts`, so the start is the same path a toggle in another tab takes rather than a special case at the install site.
- **A failed addon stays enabled.** The supervisor records `failed` with the reason and leaves the registry alone. Auto-disabling would throw away what the player asked for to record something the loader already knows, and a failure caused by the game not being ready yet would then need a manual re-enable to recover from. Reload is what tries again.
- **Everything an addon creates goes in its disposal bag, and a pending promise resolves rather than hangs.** Disable is hot, with no page reload, so a bare `setInterval` runs forever against DOM the loader has already removed. An open modal or a key-capture prompt torn down at disable resolves with a dismissal value: a rejection would run the addon's catch at exactly the moment it can no longer safely create anything.
- **`addEventListener` capture uses the OBJECT form, never the boolean shorthand.** Node's `EventTarget` accepts a boolean on add and then ignores it on remove, so the shorthand leaves the listener attached and the teardown silently does nothing. Browsers honour both, which is what makes the shorthand the version that looks fine until it is not.
- **`woc.settings` is TOTAL over what the manifest declares, so a read with a fallback beside it is dead code.** `runtime/settings/values.ts` coerces the stored value to the declared type, clamps a number into its declared `min`/`max`, drops a `select` option the manifest no longer offers, and falls back to the manifest default, on hydration and on every change. So `woc.settings['max-rows']` is already of the declared type, already in range and already present by the time an addon's first line runs. Fifteen of the sixteen addons nonetheless wrote a `settingFlag`/`settingNumber`/`settingText` triple guarding a `typeof`: 64 call sites, every fallback byte-identical to its manifest default, not one capable of ever returning, 302 lines. **They wrote it because nothing told them not to, which is what this paragraph is for.** Read the setting directly, and when deleting the `DEFAULT_*` constant check first, because several are also read as a floor in the addon's own arithmetic. Two qualifiers that look like counterexamples. An id the manifest does NOT declare reads `undefined`, and that is a manifest bug rather than a value to defend against, since the loader keys the object by declared id alone. And the clamp applies to a STORED value: the schema also refuses a manifest whose declared default is outside its own bounds (`{ type: 'number', default: 100, max: 40 }`), and `defaultValue` clamps as well for a manifest an older validator let through, which is what makes the guarantee unconditional enough to delete a guard on.
- **The four storage namespaces are split on TWO independent axes, ownership and scope.** `addon:<fqid>` is the addon's own KV, account-wide; `char:<fqid>` is the addon's own KV for ONE character; `config:<fqid>` is loader-owned settings and keybind overrides; `ui:<fqid>` is loader-owned per-character frame state. Ownership is why `config` and `ui` are not in `addon`: an addon calling `storage.set('values', ...)` would otherwise become the addon whose settings never persist, and `storage.keys()` would report loader data as the addon's own. Scope is why `char` is a namespace rather than a prefixed key inside `addon`: sharing it would put one character's keys in front of `storage.keys()` for every other character, and would let an addon's own key name collide with the derivation. The two axes are independent, which is what to check when a fifth is proposed: `addon` and `char` share an owner and differ in scope, `ui` and `char` share a scope and differ in owner.
- **Per-character state is keyed on realm plus character name, never on `pid`.** The pid from the `hello` frame is the sim's entity id for one session and is reissued on the next, so anything keyed on it scatters across a new set of storage keys every login and reads to the player as nothing ever having been saved. `perCharacterKey` in `shared/storage-keys.ts` is the ONE derivation, shared by the loader's frame state and an addon's `storage.character`, because a frame and a data key that disagreed about whose they are would be two halves of one addon restoring for two different people.
- **A per-character READ waits for the character and a per-character WRITE refuses to.** An addon's first line runs at document-start, on the landing page, where there is no character and therefore no key. A read's answer is determined when it RESOLVES, so holding it until world entry hands back the data of whoever actually logged in. A write's payload was determined when it was CALLED, so holding one would store a value computed before anyone knew whose it was against whichever character the player then picked: not a delay, but one character's data written onto another's, silently. `woc.storage.character` therefore rejects a write before world entry and names `world.ready` as the gate. Dropping it instead, which is what `kit/frame-state.ts` does, is right THERE and only there: frames are hidden before world entry, so there is provably no gesture to record, and without that argument a dropped write is a promise that resolved to say something happened.
- **The bus refuses two things, and both refusals are the design.** NOBODY RECEIVES THEIR OWN MESSAGES, on either form of `from`: an addon does not need a bus to call its own code, and self-delivery is the shortest possible loop. A SUBSCRIBER NAMES ITS PUBLISHER, `on(from, topic, handler)` rather than `on(topic, handler)`, with `bus.anySender` where any will do. That PREVENTS squatting rather than detecting it, and the difference matters: the detecting version puts a `from` check in every subscriber, and that check is the one nobody writes. `from` is stamped in the hub from the fqid the surface was built with and the message is frozen, so a sender cannot claim to be an addon somebody decided to trust.
- **A synchronous emit is capped in depth, because a runaway one is a wipe.** Delivery is synchronous, which leaves A -> B -> A reachable even with self-delivery gone, and unbounded synchronous recursion hangs the tab. `MAX_DEPTH` stops it and `diag` says which addon and topic it stopped; the counter is decremented in a `finally` so one throw cannot leave the bus muted for the session. This is also why there is no request-response and never will be: awaiting a reply from an addon that may be disabled, may never have been installed, or may simply not answer is a hang with no timeout anybody chose.
- **An addon that needs game CONTENT ships it as a committed table, and the generator that writes it reads a CHECKOUT under the same rules `pnpm aura-kinds` does.** Zone layouts, gather nodes, rare spawns and quest text are in the game's own bundle and nothing serves them, so the only alternatives to a table are to hand-type one or to do without. The file is a `.json` beside `main.js`, declared in the manifest's `data` array, and read back through `woc.data(name)`. **The declaration is what makes the surface refusable**: the argument is checked against the list, so an addon cannot reach a file it did not say it would. `.json` only, because `woc.data` hands back a PARSED value and a declared `.txt` is a file it could only fail on; at most eight files at 512 kB each, the preview's ceiling and for the preview's reason, since the player waits for this during an install they asked for and it then sits in GM storage for as long as the addon does. `DATA_MAX_BYTES` lives in `shared/addon-data.ts` because two trees enforce it, `host/addon-data.ts` at install and `tools/manifests.ts` in CI, and a second copy of the number is the one that drifts. The data is fetched where the BODY is fetched and cached beside it. `addons/*/generate.mjs` is a checkout reader rather than a manifest reader, so it inherits every consequence: `--game` is REQUIRED and never defaulted, a missing source file is a failure rather than a warning, and the checkout's version is stamped into the output. Six of the sixteen addons carry one. Regenerate rather than hand-edit, exactly as with `marketplace.json`.

  **The two argument FORMS have drifted and nothing enforces either.** `tools/aura-kinds.mjs` takes `--game <path>` SPACE separated (`process.argv.indexOf('--game')`) and refuses `--game=<path>`. Of the EIGHT `addons/*/generate.mjs`, three accept both forms (`emberwatch`, `ledgerline`, `tocsin`) and five take `--game=<path>` only (`longwatch`, `lorebind`, `trailmark`, `veinsight`, `wayfarer`). Passing the wrong form trips the required-argument error, which reads as a missing flag rather than a wrong one. Nothing is broken and no output is wrong. Accepting both everywhere, as those three already do, is the fix if anyone is in there.

  **That reading was WRONG here for at least two releases, and how it was wrong is the lesson.** This said "five of the six take `--game=` only, and `emberwatch` alone accepts both", and the reference file beside the skill said `emberwatch`, `ledgerline`, `tocsin` and `wayfarer` accepted both; the true set is the first three of those and not the fourth, and there are eight generators rather than six. Both were plausible and neither was checked by anything. **The way to check it is to RUN each generator both ways**, because the shapes of the parsers differ: `emberwatch` matches the inline form with a regex rather than `startsWith`, so reading the source for one idiom misclassifies it, and the refusals are worded differently enough per generator (`is required`, `pass --game=`, `no --game=<path>`) that grepping for one phrase misclassifies the rest. A wrong entry here costs a reader the form that works.

  **A stale table is the failure this design exists to make FIXABLE, and it does not look like anything.** Game 0.35.0 re-sited 18 gather nodes in one editorial pass. Nothing on the wire says a node moved, no 404 reports it, and no test can catch it, so a table goes on pinning nodes where the game no longer puts them: no error, no warning, just a player walking to a marker and finding an empty field. **The whole safeguard is remembering to regenerate on a game release**, which is why every generator stamps the checkout version it read into its output: that stamp is the only thing on disk that says how old the table's claims are.

### The UI kit

- **A `bare` frame accepts neither a drag nor a resize outside the arrange mode, and every other density is untouched.** `buildChrome` hands the gesture layer `handle: el` for a bare frame, because there is no title bar to grab, and the bare default is `pointer: 'content'`, which hands the pointer back over exactly what the addon DREW. So the only grabbable parts of an overlay are the rows a player reads and clicks, and before the rule any press that travelled a few pixels moved the panel: six of the frames in the catalogue were in that position. `kit/frame-gestures.ts` confines both gestures to the mode that already outlines every frame, floors it at a grabbable size and takes the pointer back over the whole box. **The gate is on the interactjs instance and never on the box keeper**, which is the only path a box is written by and serves `place` and `refit` as well as a drag: a gate there would stop a frame being restored to its saved position or pulled back on screen after the viewport shrank, which is worse than the accident it was preventing. **EVERY refused drag toasts**, naming the combo the arrange bind is actually on, because the alternative is a panel that silently does nothing. Once a session was the first shape and was wrong: a player who tries the gesture again is asking the question again, usually minutes later on another panel, and a rule that answers once and then goes quiet cannot be told from a panel that has broken. `kit/arrange-hint.ts` takes the previous message down as it raises the next, since the toaster stacks five and holds each for four seconds, and five copies of one sentence are not five answers; it reads the combo at the moment it speaks, since the player may rebind it. **This is also why the kit draws no resize edge of its own and no addon needs a grab strip:** the unreachable edge of a half-empty overlay and the accidental drag over its rows are the same mismatch between a frame's box and what it drew, and confining both gestures to the mode answers both at once.
- **Addon frames are hidden whenever the game HUD is not in the document, and the default is hidden.** The root being a sibling of `#ui` means a HUD re-render cannot take addon UI away, and the cost is that nothing takes it away when the HUD legitimately goes, so a frame sits over the landing page's PLAY button after a logout. `ui/root.ts` puts `NO_HUD_CLASS` on the root at mount and `ui/mount.ts` clears it from the HUD presence signal, so the state that needs no event to be correct is the safe one; that matters because a frame with a saved visibility is restored the moment its addon starts, at document-start on the landing page. The rule names `.woc-addon-frame`, never the root's children: the manager has to stay reachable with no game at all, since it is how a player finds out the loader is broken. Addons keep RUNNING before world entry by design, subscribing and preparing while `world.ready` is pending; what they must not do is draw over the game's own pages. `whenHudMounts` reports presence falling as well as rising, and `attached()` means "is the HUD up now", not "was it ever".
- **The root is a sibling of `#ui`, is NOT A LAYER, and its stylesheet is unlayered.** The HUD rebuilds its own subtree, so a root inside it would be swept away with whatever re-rendered. `#woc-addons` is `display: contents`, and `ui/root.ts` puts a `woc-hud-band` at `z-index: 5` and a `woc-overlay-band` at `100001` inside it. One layer on the root cannot work: `#options-menu` is a `.window` INSIDE `#ui`, so one z-index above `#ui` is one above every window the game has, the bags and the map and the spellbook included, and the game menu opens underneath an addon frame. There is no slotting between them from outside, since `#ui` is one stacking context, so the answer is two bands. `display: contents` is load-bearing: `position: fixed` ALWAYS creates a stacking context whatever its z-index, so a root with a box traps both bands in one layer again. **Which band a thing goes in is the frame/window distinction the kit already draws**: a frame is HUD furniture and goes in the hud band, under any window the player opened; the manager, menus, toasts, modals, the banner and the tooltip go in the overlay band. World anchors are hud, because a label over a mob is not something the player opened. The price is that the game's chat and action bars cover an addon frame, and that is the right way round. Two consequences that are easy to miss: `#woc-addons > *` became `#woc-addons :where(.woc-hud-band) > *`, and the `:where()` holds the rule at (1,0,0) so `#woc-toasts` and `#woc-tooltip` in `kit.css` still turn the pointer back off on source order, and it is TWO rules rather than one `:where(a, b)` because the build's scoping guard splits a selector list on commas and reads the second half as unscoped; and an addon reaching `frame.el.parentElement` finds a band rather than `#woc-addons`, which is unsupported either way.

  **An unlayered rule outranks any layered one whatever the specificity**, so addon styling survives a game update that adds a layer or reorders the ones it has. The game's layer order (`@layer tokens, base, layout, components, hud, shell, hud-mobile, index-extra, play-extra;`, declared identically in `play.extra.css` and `index.extra.css`) is unchanged since at least 0.34.0. **Not every game rule is in a layer:** `#proc-overlay` and `.breath-bar` sit at the unlayered tail of `src/styles/hud.css`, so they compete on ordinary specificity and source order rather than losing by construction. That costs nothing today, because both sets are scoped to their own elements and the loader's sheet is injected later, but it would cost something the day a class the kit WEARS left a layer: `panel`, `panel-title` and `x-btn` are all inside `@layer base`, and if one left, the loader would start winning by injection order, which is much weaker and would fail silently. The flip side is that these rules also outrank the game's, so they stay scoped to loader-owned elements and `loader/build-runtime.mjs` enforces that. The scoping rule has ONE exception with a different check behind it: a `@keyframes` block's interior is `from`, `to` and percentages, which match no element, so the build strips those blocks before reading selectors and checks the animation NAME instead. That name is global to the document and must start with `woc-`: an unprefixed one shadows a game animation of the same name, and the symptom is the game's own element animating wrongly.
- **A frame's `pointer` decides how much of the player's controls it takes away, and a bare one is `content` by default.** The game binds the world's `mousedown` and `wheel` to the CANVAS, so an element over it does not cover a click, it consumes the gesture: targeting, right-drag camera look and wheel zoom all stop inside that box. Nothing can forward them on, because the loader's root is not an ancestor of the canvas and a synthesised event is both untrusted and against the no-synthetic-input rule, so `pointer-events` is the only lever. `auto` is the whole box; `content` makes the box transparent and leaves what the addon DREW live, so gaps and dead width fall through while rows keep hover and tooltips; `none` is inert. The default is per density because the densities mean different things: a panel with holes in it is a panel that sometimes ignores the player, while a bare overlay's empty half is INVISIBLE, and solid by default it is a rectangle that swallows clicks while showing nothing, which is exactly what an empty resizable bare strip is, since `interactive.ts` writes an explicit width and height only for a RESIZABLE frame. **This is the game's own idiom**: every read-only overlay it draws is `pointer-events: none` (`#nameplates`, `#perf-overlay`, `#aura-overlays`), and the aura overlay takes the pointer only under its `.placement` class. The unlock mode is ours and forces every frame back to `auto` for the same reason. With `content` you grab the frame by something it drew, so a drag or an edge resize works over a row and goes to the game over empty space; interactjs still starts a drag from a child of a `pointer-events: none` element, verified in a real browser over CDP, because the press lands on the row and matches the interactable by bubbling. A tooltip cannot survive `none`, and the hit-test-on-pointermove workaround was rejected: it re-derives what the browser already knows, on every move, while the player is playing.
- **Window order is ONE service on the root, never per window.** Loader windows are absolutely positioned siblings with no z-index, so without `ui/kit/stacking.ts` overlap falls out of DOM order and clicking a buried window leaves it buried. One capture-phase `pointerdown` plus `focusin` on `#woc-addons`, resolving `closest('.woc-window')`, covers the manager and every addon frame with no per-surface wiring, so any window a future feature adds participates the day it lands. Capture phase because a child that stops propagation must not be able to bury its own window; `focusin` because tabbing into a buried window and staying buried is the keyboard version of the same bug. A frame is also raised when BUILT and when SHOWN, since a window nobody has clicked holds no z-index at all and would open under everything clicked so far; hiding is deliberately not a stacking event. **Raising belongs to the act of SHOWING, not to a caller**, because a per-route wrapper is a list of callers that has to be complete: the manager raises itself from `show()` in `ui/manager/index.tsx`, finding its own window by `[data-woc-manager]` since `.woc-window` is every addon frame too, and it raises even when the window was ALREADY open. **The counter renormalises at `WINDOW_Z_CEILING` rather than running away**, so the overlay bands in `styles/kit.css` (toasts, modal, tooltip, which start one above it) are above EVERY possible window; dead windows are dropped on the way. Keep the CSS values and the ceiling in step.
- **A window's placement rules are pure, and its gestures are not.** Everything a player can notice (a window cannot be dragged somewhere it can never be dragged back from, a restored position survives a smaller monitor, a persisted box is validated before it reaches a style property) lives in `ui/frame/geometry.ts` with a Node test. interactjs handles pointer capture, touch and edge hit areas, and nothing else. A NaN reaching a style property drops the declaration silently rather than raising, which is why the persisted box is parsed rather than trusted.
- **The unlock outline is an `outline`, and the bare density is why.** `density: 'bare'` strips its chrome by resetting `border` and `box-shadow` at a specificity the unlock rule does not beat, so drawing the outline as either would put it on every frame EXCEPT the empty overlay the mode exists for. It is drawn LOUDLY on purpose, with a wash over the frame's area: an outline around an empty bare frame is a rectangle around nothing, which says where a border is without saying there is anything there to grab.
- **A non-resizable frame is given its declared `width` as a WIDTH, and no height at all.** `frame/interactive.ts` paints a size only where somebody can drag one, which is right for the height and wrong for the width, because a shrink-to-fit element is sized by its content in BOTH directions, so a frame blows past its declared width the first time one of its own lines is a sentence. A `max-width` in `applyWidth` (`kit/frame.ts`) fixes the overflow and not the MOVEMENT, because under a ceiling the width still follows the content, so the panel steps in and out as its own rows reflow, under the eye of the player who caused it. So it writes `width`, and writes it whether the addon named one or took the default, since an addon that never thought about its width is precisely the one whose panel would otherwise move. There is deliberately no equivalent for the height: a bounded frame clips itself rather than growing, and nothing on screen says a row is below the fold. An addon must not work around this by sizing its own column to the frame width, because the frame's padding is inside that number. **Nothing in Vitest can see any of this**: the suite pins that a width is WRITTEN, and the stage is what proves the box holds still.
- **A readout's height is the KIT's to derive, and an addon that writes one itself opts out of the tap-target floor.** `ui.bar` takes `size` the way `ui.tile` always has, and both hand the number to a custom property the sheet derives everything else from. The property is UNITLESS on a bar and pixels on a tile, which is not a style difference: `styles/bar.css` derives the TEXT as an `em` so a natural-height row reads at whatever size the player's game is set to, and calc cannot divide a length by a length to reach that ratio. Five addons had written the derivation out by hand, transcribing this kit's own 18px icon box to scale the art, and `cadence` argued its way past the floor rule on the grounds that `touch.css` does not name `.woc-bar`, which is a fact about the sheet rather than about the addon. **`ui.units` is the arithmetic under all of it**, and the two decisions worth having in one place are that the gaps come out of the box BEFORE the division and that the share is FLOORED: a share rounded up is a last row past the bottom of a box that clips rather than scrolls. **`frame.box()` is where the number being divided comes from**, and it exists because `onMove` deliberately does not fire for the initial placement, which every scaling addon had answered by seeding a copy of the opening size.
- **`resizable` is per axis, and the axis an addon does not hand over follows its content.** `'width'` and `'height'` are the same option answering one axis; `veinsight` and `wayfarer` had each written a comment refusing to be resizable at all, because their row count is a setting and an owned height could only clip the rows or leave a gap under them, and both gave up the width with it. An unrecognised value falls back to NOT resizable rather than to both, which is the cheaper failure: a frame that owns an axis it should not clips its own content.
- **A `.woc-bar` never shrinks, and the rule is one line of CSS with no test behind it.** A screenful of bars is a column flex container and a flex item shrinks by default, so with more rows than the frame is tall every row is squeezed and the bar's own `overflow: hidden` cuts its second line off rather than the list scrolling. `flex-shrink: 0` in `styles/bar.css` is the whole fix, and it cannot be tested from Vitest, where every `.css` import resolves to `''`. This is what the stage is for.
- **Frame density is an enum, and the default is the game's own scale.** `ui.frame`/`ui.window` take `density: 'comfortable' | 'compact' | 'bare'`. Comfortable is what the game draws its own windows at on a desktop and is the default, so an addon that has not thought about it looks like part of the game; compact is tighter than the game's own panels, for a dense readout an addon GLANCES at; `bare` drops the panel, the padding and the title bar and keeps everything else. An enum rather than `compact: true` because the axis has more positions in it and a flag set turns into a matrix nobody can reason about. `ui.window` refuses `bare` ONLY and falls back to comfortable, because a window's close button lives in the title bar that `bare` removes and a panel the player cannot dismiss is worse than one drawn more heavily than asked for; it honours `compact` normally (`frame-chrome.ts:44`). An unrecognised value falls back to comfortable, never to compact: the failure to avoid is a typo silently dropping the floor. The variant also reaches `.woc-btn` and `.woc-tab` inside the frame, which is what makes reusing those families the right move for an addon instead of restyling its own.
- **Which of frame and window an addon reaches for is decided by the ARIA ROLE.** `roleFor` is the whole of it: a window is `role="dialog"`, a thing the player OPENED, and a frame is `role="group"`, HUD furniture that lives on screen. Three things that look like the difference are not: the close button is `closable` and works on either (`closeFor`, gated on density rather than chrome, and a window merely defaults to having one); the game's `panel` border and background are worn by any non-`bare` density; and resizing is its own option. So a HUD surface the player toggles is a `frame` and a surface the player opens to read and dismisses is a `window`, because that is what a screen reader announces and it should be true. Everything built so far binds a toggle, so everything is a frame, and a frame that wants a mouse route to dismiss it passes `closable: true` rather than becoming a window. A bare frame is dragged by its own CONTENT, which is also why the unlock mode exists: an overlay whose list is empty is zero pixels, and zero pixels cannot be grabbed.
- **The tap-target floor is a TOUCH rule, and reading it as a universal one makes every loader panel a third larger than the game beside it.** The game holds 16px type on a 40px target under `@media (pointer: coarse)` and nowhere else: `base.css` floors every focusable control there, at 16 because iOS Safari auto-zooms below it and ignores the viewport scale-lock; `components.css` gives `.ui-dd-item` its 40px in the same query, since the global floor covers input/textarea/select and misses a custom select trigger, which the kit's `picker.ts` is; `hud.mobile.css` gives the bank tabs theirs under `body.mobile-touch`. On a DESKTOP the game runs 11px to 13px throughout: `.bank-tab` and `.delve-tab` are 13px on 7px of padding, `.btn` is 12.5px on 6px, `.ui-dd-item` is 12px on 5px, `#tooltip` is 12px, `.panel-title` is 15px, and `.x-btn` is 14px with no minimum at all. The floor is not gone: `ui/styles/touch.css` is the same query, concatenated LAST so it beats the density variants at (1,2,0) and reaches a compact frame as well as a comfortable one. **What follows for an ADDON is that hand-sizing a kit control defeats it**, because an inline style outranks every selector a stylesheet can spell, so a font size written onto a field is silently opting out of an accessibility rule on a phone. Change the PADDING, never the font size or the height. **The rule generalises: a number copied out of the game is only as true as the query it was copied from.**
- **A bar's fill is tinted by SCHOOL, and the palette is the game's.** `ui/kit/bar.ts` takes `school` as an axis separate from `tone`: tone is urgency, a school is what kind of damage a row is made of, and folding them into one enum would make `tone: 'frost'` and `tone: 'danger'` look like alternatives to the same question. The colours are `--color-debuff-*`, which the game publishes for its own debuff borders, so a tinted row matches what the player reads on an aura icon; no addon may pass a colour, because two addons colouring by school should look the same. Tone wins over school where both are set, by SOURCE ORDER in `styles/bar.css` at equal specificity, which is why the two groups there carry a note not to reorder them. **Rank and share were both rejected as the colour axis**: a row already encodes rank by its position and share by its fill width, so either would be a third encoding of a fact already on screen, and rows would swap colours whenever the ranking shifted, which is exactly when you want to keep tracking one ability.
- **A DROPDOWN IS THE KIT'S MENU, and a native `<select>` is not usable here at all.** Its popup is drawn by the operating system: outside the document, in the system font, beyond every rule the loader has, so a filter row opens a white system list in the middle of a dark fantasy HUD. The game reached the same conclusion, and `.ui-dd` in its own stylesheet is a button, a caret and a menu with the chosen row in gold, which is what `kit/picker.ts` is. It reuses the EXISTING menu rather than adding a second popup, because `ui.menu` already owns the four ways one has to close and a hand-rolled dropdown gets three of them right; `MenuItem.checked` marks a choice-menu row, drawn in the accent and announced as `aria-checked`. TWO renderers, like the close mark: `kit/picker.ts` for plain DOM and `manager/picker.tsx` for the manager's preact, over one caret geometry in `kit/caret-glyph.ts`. **A suite that drove the old control still passes and proves nothing**: a `<button>` carries a `value` property too, so assigning one and reading it back is green while the manager is never told anything. `tests/fakes/controls.ts` drives the real thing and `menuService` in `tests/fakes/ui-deps.ts` is why every manager suite has a real menu to drive.
- **ITEM QUALITY is a third axis of the same kind, and the two tables it needs live apart on purpose.** A tier is what a player picks an item out of a grid by before reading a word, so `ui.bar` and `ui.tile` take `quality` beside `tone` and `school`, and `woc-quality-<tier>` is published as a class an addon may put on anything it owns, the way `.woc-btn` and `.woc-tab` already are. **The palette is the game's and is NOT a token**: it publishes `--color-quality-default` for an item it ranks at no tier and hard-codes the six, in TWO tables that differ at one tier, `QUALITY_COLOR` in `src/ui/icons.ts` for a NAME and the `.q-*` rules in its own sheet for a BORDER, where common is white as a word and a dimmer grey as an edge. Both are transcriptions with the same standing as the item table an addon has to carry. The name table is in `styles/quality.css` and the border table in `styles/tile.css`, and the split is the CASCADE rather than taste: `.woc-tile` sets `border` as a SHORTHAND, so a tier declared earlier is overwritten wholesale and one declared after the school and tone groups would win a border that belongs to urgency. The three groups in `tile.css` are one ordered run, tier then school then tone, each winning from the one before. Nothing under Vitest can see that: the suites pin the CLASS and the order is checked by running the loader on the stage.
- **There is ONE close mark, in `ui/kit/close-glyph.ts`, rendered two ways.** `×` is MULTIPLICATION SIGN and inherits the title bar's serif font, so it renders thin and off-centre and visibly not the mark the game's own close buttons use. It is a stroked path, using `currentColor` so the existing hover rule reaches it, with the `aria-label` kept on the button because a path cannot be read aloud. The geometry has one home and two renderers, because the frame builder is plain DOM and needs markup while the manager is preact and would otherwise need `dangerouslySetInnerHTML` for something that does not need it. Both `tests/ui-kit-frame.test.ts` and `tests/manager-render.test.tsx` assert against `CLOSE_PATH` by name, so a renderer that goes its own way fails there rather than in a screenshot. **A glyph never goes in a strings module:** strings are text a translation pass would touch, and a translated close mark is nonsense.
- **CSS text is not readable from a Vitest suite.** Every `.css` import resolves to `''` there (`LOADER_CSS` measures 3 characters, the joining newlines), and `?raw` does not change it because vite's own CSS handling wins. So a suite can pin the class a module WRITES but not the selector the sheet declares; reading the file would need `node:fs`, and `noNodejsModules` is not exempt in `tests/**`. The agreement between a class name in `ui/kit/` and its rule in `ui/styles/` is checked by running the loader. Do not widen the exemption table for it.
- **A tooltip whose anchor leaves the document is the KIT's problem, not the addon's.** `pointerleave` never fires on an element removed while the pointer is over it, so a tooltip on a dropped row floats with no event able to clear it. The attachment outlives the element too, so a list that rebuilds rows leaks one registration per row per rebuild into the addon's bag. `ui/kit/tooltip.ts` owns both. The visible one is a MutationObserver that runs ONLY while a tooltip is shown, scoped to the loader's root rather than the document, since addon DOM is there and the game's HUD is not; a body-level subtree observer would wake on every HUD change at snapshot rate to answer the same question. The leak is swept on the next `attach`, which is the moment a rebuild is definitely happening, rather than by an always-on observer. **An attachment is not reaped until it has been seen CONNECTED**, because an addon legitimately attaches before inserting; the observer therefore also checks the shown anchor directly, which is the one case the sweep cannot reach. None of this is on the public API: an API where an author pairs an attach with a detach on a lifecycle the loader owns is an API whose leaks belong to whoever forgot.

### Keybinds

- **The keydown listener claims a key ONLY when a bind matched.** The loader's dispatcher runs in the capture phase, ahead of the game's own handler, so `stopImmediatePropagation` is a decision about whether the game gets to act at all. Calling it eagerly quietly degrades the controls of a game the player is still playing, and nothing reports it. The editable-element guard is deliberately WIDER than the game's, which checks only input and textarea: declining where the game would act costs one keystroke, acting where the game declines eats a character out of something the player is typing.
- **Conflict detection reads the game's LIVE keybind profile, not localStorage.** `__game.input.keybinds` carries the game's own matchers and every DEFAULT binding. The stored blob holds only what the player explicitly saved, so on an account that never opened Key Bindings it is empty and every key reads as free. Storage is the fallback, and the reading carries a `source` so the manager can say the answer is incomplete rather than presenting it as clean. Held actions (movement) match the bare code with modifiers ignored while edge actions match the whole chord, and the stored string does not say which it is, so the fallback over-reports on purpose. Reading the live profile is also what makes a game release that ADDS a default binding cost nothing here: 0.37.1 added `targetPrev` on `Shift+Tab`, and a conflict against it was reported correctly the day it shipped with no table in this repository to update.

### The marketplace, the dev server and the manager

- **The official marketplace cannot be removed.** `canRemoveMarketplace` is called in the host, not the UI, so a hand-crafted call from the runtime still fails.
- **The local dev source is a build-time constant, not user input.** `LOCAL_ORIGIN` in `shared/marketplace.ts` is what puts `localhost` in the userscript's `@connect` list, and `normalizeMarketplaceUrl` rejects it like any other non-GitHub host, so the set of origins the loader can reach is still fixed at build time. `MarketplaceSource` is a union rather than an optional field so a caller building a URL has to say which kind of source it is looking at.
- **A marketplace id is re-derived on read, never trusted from storage.** Only the owner, repo and ref a user actually chose are persisted; `fromStored` re-runs the same validation that accepting them did. The id is the storage namespace of every addon installed from that source, so a stored id a player could edit would point one source's addon at another's settings and data.
- **The dev watcher polls BODIES, never the index.** A new addon directory or an edited manifest needs an explicit refresh. Index polling would emit a `market.changed` on every tick and repaint the manager continuously to report that nothing moved.
- **The dev server serves the loader itself, and that route is ONE EXACT PATH.** `resolveFile` guards a directory against traversal; `resolveLoader` matches `/woc-loader.user.js` and nothing else, so there is no second tree to walk in a server whose only real security property is that it has exactly one. The name lives in `tools/artifact.ts` because vite writes the file and the server hands it out, and a rename on one side would leave `pnpm dev` answering 404 while the build reported success. Installing over http rather than `file://` is deliberate: the file permission is off by default and moves between browser versions, so it turns "did the install happen at all" into the first thing to debug.
- **The dev server's index is generated per request and its `generated` stamp is an mtime, not a clock.** The ETag is taken over the response body, so a timestamp in it would make every index request a fresh body and the conditional GET would never answer 304.
- **The contents-API fallback is reached only on a 404, and only for a repository.** A 403 is the unauthenticated rate limit, and answering it with one request per addon would spend what is left of the hour discovering there is no quota. A repository whose `addons/` listing 404s too is one the loader cannot see at all, so the error reported is the one about the index the player was looking for. A repository with more directories than fit in the quota is REFUSED rather than truncated: reading the first forty and presenting them as the source's contents would be a silent lie about what it offers.
- **`MarketApi.setRef` moves where a source reads from and never its id.** The id is derived from owner and repo, so everything installed from that source keeps its fqid and therefore its settings, keybinds and data. The cached rows are dropped on the way, or a failed read of the new tag would leave the previous tag's addons on screen under the new tag's name.
- **Nothing about an addon is written anywhere but that addon's own manifest, and the site and the README both read it from there.** Both publishers go through `tools/catalog.ts`, the same `readAddon` `pnpm validate` and `pnpm index` use, so nothing published can describe an addon the loader would refuse. The rule breaks in one shape, a SECOND description: a map beside the catalog cards saying what each addon adds, a paragraph per featured addon, a hand-written list in the README. Each covers the addons that existed the week it was written and still describes that handful when there are thirty-one. **The only thing either publisher decides is WHICH four addons get a picture**, in `tools/featured.ts`, shared so the site and the README cannot pick different favourites; everything on such a block is the manifest's own name, version, tags, description and alt text.
- **The catalog a PLAYER reads is not the whole marketplace, and the difference is a tag rather than a list of ids.** An addon tagged `development` is a tool for addon authors: `dev-harness` ships, is in the in-game Browse, and is off the site's catalog page and out of the README's list. Derived from the manifest so an author tool added later is filtered the day it lands, and both publishers NAME what they left out rather than quietly shortening the count, because a site saying 31 where Browse offers 32 is a bug report against whichever one the reader saw second.
- **A generated file is owned by the BOT or by the contributor, never by both, and the README is the bot's.** `marketplace.json` has never had a freshness test: it is regenerated on main and a contributor is not asked to run `pnpm index` before pushing. The README's addon section is written by the same job in the same commit, so it works the same way and has no freshness test either. **What IS tested is the pair of markers**, since `pnpm readme` reads their absence as "no generated section here" and stops silently. The rule generalises: test the thing that would stop the generator, never the output the generator is responsible for.
- **Both derived files are regenerated by ONE job, and one job is what keeps them from racing.** `marketplace.json` and the README's addon section come from the same manifests and are both pushed to main by `.github/workflows/marketplace.yml`. As two workflows on the same event they would check out the same commit and the second push would be rejected as non-fast-forward, a failure that appears only on the day both files change. One job, one commit, and the title says which of the two moved, because it becomes a `CHANGELOG.md` line.
- **Never hand-edit `marketplace.json`.** It is generated by `pnpm index`. The dev server does not read it at all: `tools/serve-core.ts` builds its own index from `addons/*/addon.json` on every request, through the same reader `pnpm validate` uses, so a manifest saved mid-session is visible on the next refresh and the dev index cannot diverge from what CI would accept.
- **The manager has three independent ways in, and one of them is not in the game.** The game-menu entry and the rail button both live in game DOM and can be taken away by a game update; `GM_registerMenuCommand` is host-side and cannot. That command is registered whether or not the runtime ever connects, and a failed bridge handshake costs the registry rather than the UI, because the manager is how a player finds out the loader is broken.
- **The manager's reading path fetches AT MOST ONCE A SESSION, and the once is not optional.** `market.list`, `registry.list` and `registry.updates` all answer from what the host already holds, and Refresh is the only control that always fetches: an update badge that decided to fetch would put a request per marketplace in front of every open of the window, which is the version of the feature that gets switched off. The three marketplace panes share one `catalog-store.ts` for the same class of reason, since three copies of "the source list plus the installed set" would go out of date independently and Browse would offer an Install for a source the Marketplaces pane had already removed. **Something has to pay the once.** The index cache in `host/market-indexes.ts` is per session, so without a seeding read Browse draws "no marketplace has been read yet" until the player finds Refresh, and `registry.updates` compares installed addons against no rows and answers that nothing needs updating, which is a false all-clear and the worse of the two because it looks like an answer. `market.ensure` closes it, awaited AHEAD of the three reads in `catalog-store.ts` rather than beside them, since all three read the cache it is still filling. The once-per-session refusal lives in the host, not the store, so a second caller cannot turn it back into a fetch per open; a source whose read FAILED counts as read, or the retry would be the doomed request in front of every open. It is affordable because of the fetcher's ETag cache: the seeding read of a second session is a 304 with no body.
- **A companion is a NOTE with a route, and its two halves live in two keys.** `companions` is the id and `companionReasons` is one sentence per id saying what that addon ADDS. The second key exists because a description was doing that job, and a description is read before the player knows the companion exists, cannot say whether they have it, and goes stale the day the relationship changes. **It could not be a richer shape for `companions`, and that is the load-bearing half.** A marketplace index is parsed as ONE `z.array(MarketplaceEntry)`, so a single entry an older loader cannot read fails the whole index and takes that source dark for every player still on that loader; an unrecognised KEY is dropped, which is the compatibility the manifest docs already promise. The tie between the two is enforced rather than trusted (`AddonManifest.refine`: every reason key must be a named companion), because two keys describing one relationship is the shape that drifts. **The field gates nothing, and its actions are not a second path to anything**: Enable is the Installed pane's own toggle pointed at another row, Get sets the same `confirming` state the row's own Install sets so the SAME confirmation renders, and Find it moves to Browse with the search filled. Every action is a jump into a control that already existed, because a second install path is a second thing to keep honest. Two things follow that are easy to get wrong: the pending row is resolved against EVERY row rather than the filtered ones, since a player pressing Get has almost always searched for the addon that named the companion; and Browse's search is held by `ManagerApp` rather than `BrowsePane`, because Find it switches tab and a pane that owned its filter would be rebuilt empty by the switch.
- **A pin means "stop offering", never "install that instead".** A marketplace serves one version per ref, so there is no older body to go back to. `registry.setPin` fetches nothing; it takes the addon out of the update list and out of "update all". The row stays visible carrying its pin, because the only thing a pin needs a UI for is saying that an update exists and that the player's own decision is holding it back.

### Versioning and release

- **`@name` and `@namespace` are FROZEN, and freezing them is the same rule an addon id has.** A userscript manager keys a script's identity, and therefore its whole GM value store, on that pair. Changing either is not a rename: it is a new script with an empty registry, so every player loses their installed addons, settings, keybinds and saved window positions, while the old script sits alongside it still running. The comment lives on the fields in `vite.config.ts` where someone editing them will see it, and `release.yml` greps the built block for both, because a comment is not a gate. The download URL, the match list and the description are all free to change; those two are not.
- **`API_MINOR` moves on the first additive merge after the current one has SHIPPED IN A RELEASE TAG, and every additive merge before that release rides it.** A minor is a claim about a surface a player can actually install, and it has exactly two observable consequences: `runtime/supervisor.ts` refuses an addon whose declared minor exceeds what the loader implements, and `host/updates.ts` keeps that addon out of the update list. Both compare against a loader somebody is RUNNING, and the only artifact is the release asset. So while no tag contains the current number, no addon can be running against a loader that claims it, the failure a fresh bump would prevent cannot occur, and bumping again would assert that a distinct targetable surface existed when nothing an author can install ever implemented it. Check with `git tag --contains <the commit that set it>`: empty means keep riding. A member changing SHAPE or leaving moves `API_VERSION` instead, whatever the release state.

  **WIDENING A UNION an addon can only READ is additive, and the precedent is `ResourceType` gaining `'focus'` at game 0.36.0.** The mechanical reading sends any shape change to the major, and it is wrong here for a reason worth stating once so the next one does not get re-argued: nothing an addon can write produces a `ResourceType`, it is read off an entity, so every existing comparison still compiles and no working addon breaks. The direction that DOES break one is a member leaving, and that is still the major. The test is which side of the API the value crosses, not whether the type text changed.
- **`apiMinor` counts PUBLISHED MEMBERS, not loader work, and a field on a record is a member.** The declaration is the smallest minor carrying every member the addon reads, and the test is one question: was the thing you read published at a minor, and which one. Whether the loader IMPLEMENTS anything for that member is not the test and must never become it. **The tempting wrong answer is to reason from passthrough**, that a decoded event or a market page reaches the addon verbatim so any loader hands the field over. It is wrong for three reasons: passing through rather than projecting is an allocation decision recorded in `world/market.ts` and nothing in the published types promises it, so an addon built on it is built on something nothing keeps true; it cannot be applied without reading loader internals, which makes it a rule two competent authors apply differently, and did; and its failure is the silent one, since an under-declared addon reads `undefined` and reports zero rather than being refused, while an over-declared one fails cleanly with a message naming the fix. **The bump and the declaration are two halves of one contract:** a field worth moving `API_MINOR` for is worth declaring against, and if reading it does not warrant the declaration then publishing it did not warrant the bump.
- **An addon's `version` is the ONLY thing that ships it, and deciding it is a judgement about the SET of changes rather than any one of them.** `host/updates.ts` offers a row only where `isNewerVersion(available, installed)` holds, so an addon changed without a bump is an addon changed for nobody: no badge, no row in the update list, no error, and the marketplace index cheerfully serving the new body to anyone installing fresh while every existing player stays on the old one. A branch that changes many addons and bumps a few leaves the rest bound for no player, corrected data tables among them, which is the kind of repair a player can never discover for themselves. That is also what completes the committed-table rule: regenerating a stale table only makes the failure fixABLE, and the bump is what fixes it. **Nothing per-change can catch this.** Every author verified their own work correctly; the omission exists only in the set, so it is visible to whoever looks across the branch and to nobody else. The test is what a player can OBSERVE, not whether bytes moved: a regenerated version stamp with identical content, or a comment, gives a player nothing, and a bump there is a download that says nothing changed.
- **The git tag is the only source of a release version.** `package.json` stays at `0.0.0` in the tree on purpose and `vite.config.ts` deliberately does not set `userscript.version`, so vite-plugin-monkey falls back to it. `release.yml` runs `pnpm pkg set version` from the number typed into its dispatch form before building and then greps `@version` out of BOTH built files to prove the stamp took. Keeping a version in the tree as well would be a second place it can disagree from, and the disagreement is silent in the worst way: a manager comparing an asset that claims the wrong version either never updates or reads a release as a downgrade. A local `pnpm build` reports `0.0.0`, which is exactly what an unreleased build is.
- **A release is ONE BUTTON, and the tag is what the run PRODUCES rather than what starts it.** Actions, Release, Run workflow, the version typed into the form: `release.yml` is `workflow_dispatch` only, and it creates and pushes the tag itself. It cannot be the other way round, because an event triggered by `GITHUB_TOKEN` starts no workflow run, so "push a tag and let the tag trigger the release" costs a personal token or a GitHub App, which is a long-lived credential that can write to main kept in the repository for no reason but to let one workflow start another. `workflow_dispatch` and `repository_dispatch` are the documented exceptions to that rule, which is how the same run reaches the deploy (`gh workflow run site.yml`) and also why `site.yml`'s `release: published` trigger has never once fired: every release here is created by that token. **Everything that can fail happens before the tag push, which is the point of no return**, and the guards are in that order for that reason. After it there are three windows and none of them costs the artifact: a failed release creation leaves a tag with no release, which is deleted and re-run; a failed publish or changelog leaves a correct release standing. **The drift guard is the one that is new rather than moved.** `marketplace.yml` regenerates the index and the README in a commit of its own, AFTER the commit that changed a manifest, so a release dispatched in the minutes between the two tags a commit whose index does not describe the addons in it. `release.yml` refuses on that, and the remedy is to wait for the bot rather than to regenerate here, since a generated file is owned by the bot or by a contributor and never by both. It compares the ROWS and not `generated`, which records the commit the bot was reading rather than anything about an addon.
- **There is no npm token in this repository and there must not be one.** npm revoked every classic token on 2025-12-09 and will not issue another; a granular token with write access is capped at 90 days, so a secret would expire four times a year and fail on the one day it is needed; and the 2FA-bypass kind loses direct publishing around January 2027, after which it can only stage a publish that a human then approves. So a token is not a shortcut past this, it is a slower version of the same problem with a deadline on it. The `types` job publishes over TRUSTED PUBLISHING instead: `id-token: write` is exchanged for a credential that exists for the length of one job, nothing is stored between runs, and npm generates the provenance attestation for free. **npm matches the WORKFLOW FILENAME**, `.yml` included and case-sensitively, against a publisher configured on the package, so the publish step cannot move to another file without editing npmjs.com in the same change, and it cannot move into a `workflow_call` reusable workflow at all, since npm validates the CALLING file's name rather than the one holding the command. Two smaller ones: a publisher created after 2026-05-20 must have `npm publish` ticked under allowed actions or every run 404s, and `setup-node`'s `registry-url` is deliberately unset, because it writes an `.npmrc` carrying an `_authToken=${NODE_AUTH_TOKEN}` placeholder that a registry rejects as a bad credential before OIDC is ever reached.
- **There is ONE canonical artifact and nothing may host a copy.** The GitHub Release asset, reached through the `releases/latest/download` redirect. `loader/dist/` is ignored and is never committed, on a tag or otherwise. Pointing `@downloadURL` and `@updateURL` at `raw.githubusercontent.com` on `HEAD` for a path `.gitignore` excludes is a 404 that nothing reports: a player whose update URL 404s gets no error, no badge, and no updates ever. `@updateURL` points at `woc-loader.meta.js`, the metadata block alone, so an update check is 1.6 kB rather than 486 kB. Both files are built in one run and attached together, or a version check answers about a build nobody shipped.
- **A published release is immutable.** A defect found after publication is a new patch tag, never a re-upload: a replaced asset under one tag means two different files claiming one version, and every checksum, cache and mirror that saw the first one is now wrong with nothing to indicate it. Deleting a release is acceptable within minutes and before anyone could have installed; after that it is a patch.
- **`CHANGELOG.md` is generated from commit titles, and the VERB is the category.** Never hand-edit it. This works because of a convention this file already imposes: a title is a capitalized imperative verb phrase with no type prefix. `Add the net and world read surfaces` is an addition and `Build the runtime bundle before linting` is a change, so `cliff.toml` groups on the verb rather than on a prefix. The practical consequence is that the catch-all files anything unrecognised under Changed, so a title that buries its verb ("Support for X") is categorised correctly by accident at best: lead with the verb. `tag_pattern` restricts git-cliff to `v[0-9]*`, or a `types-v*` tag would end a loader release section and take its commits with it.

### The stage and previews

- **A stage scenario states what was ALREADY TRUE in `world`, and what then HAPPENED in `run`, and the split is not stylistic.** `world` runs before the addon body is evaluated; `run` runs after it has mounted and drawn. An addon reads the world on its first line, so a fact stated late is one it reacted to rather than one it started from, and those are different pictures. It usually still looks right, which is what makes the exception expensive: a scenario that sets `templateId` after mounting gets rows built before there is a class to file skill art under, so the ability the game DOES ship art for draws blank next to one it does not, which reads unmistakably as a bug in `icon.ability`. **The rule: anything a session would have at login goes in `world`.** The class, the spellbook, the bags, the party. When in doubt, `world`.
- **An addon that adopts `woc.paint` has changed which LOOP draws it, and its scenario has to be told as well as its suite. The scenario half photographs a BLANK PANEL into the committed preview and nothing warns.** `woc.paint` coalesces onto the loader's own animation-frame loop instead of the addon arming its own `requestAnimationFrame`, and neither environment that stands in for a browser drives that loop by itself. A suite calling only `vi.advanceTimersToNextFrame()` has advanced a clock nothing is listening to and needs `harness.frames.tick()` beside it; a stage scenario needs `stage.frame()`. **The suite half is loud and the scenario half is silent, which is the whole reason this is a rule.** A red suite is a red suite; a scenario that never ticks reaches `data-stage="ready"` with an empty frame, `pnpm shots` photographs it, crops it to the union of frames that drew nothing, and writes the result into `addon.json` as the picture a player reads in Browse before deciding whether to install. Nothing in `pnpm check` looks at a PNG. Adopting `woc.paint` is three edits, the addon, its suite and its scenario, and the third is checked by opening the capture.
- **The stage starts from an EMPTIED player, and the emptying is deliberate.** `liveEntity()` carries `cooldowns: new Map([['aimed_shot', 4]])` because a suite wants a non-empty collection to assert against. In a photograph that is a lie: every addon reading cooldowns would draw a row for an ability its scenario never mentioned, and it would be in the corner of their Browse thumbnail forever. `createPlayer` in `stage/src/stage.ts` clears the dynamic collections there rather than changing the shared fixture, because a suite asserting on that Map is asserting on something real.
- **The loader inherits the game's look through TWO channels, and a stage that copies only the first renders a frame with no edge.** The obvious one is `var()`: every rule in `runtime/ui/styles/` is scoped to a loader-owned element, so the palette, the faces and the radii all arrive as tokens. The one that is easy to miss is that the kit deliberately WEARS three game classes: `panel` on a frame, a tooltip, a modal and a menu, `panel-title` on a title bar, and `x-btn` on a close button, so those surfaces inherit the game's own border, background, shadow and title face instead of keeping a copy that would drift. **`.panel` is where a frame's 2px border, its outline and its three shadows live**, so tokens alone do not reproduce one: with the tokens and without the rule, every colour is right and the frame has no edge at all. `pnpm theme` takes both, each rule wrapped back in the at-rules it was found in: the LAYER keeps the loader's unlayered sheet outranking the game exactly as it does in the real thing, and the MEDIA query keeps a `forced-colors` override out of an ordinary screenshot. `tools/kit-classes.ts` reads the kit and `tests/tools-theme.test.ts` fails when it wears a class the extractor does not know about, because the failure is otherwise silent.
- **A preview is CROPPED to what was drawn, and the scale is chosen so it fills the slot.** Placement is not a thing a scenario has to arrange: `pnpm shots` takes the union of every `.woc-addon-frame` rect plus 24px for the panel's `0 2px 16px` shadow, so where a frame sits in the viewport never reaches the file. What it cannot fix is SHAPE. `ui.frame` floors a frame at the size it opened at (`sizeBounds` defaults `min` to the declared size), so a seeded box SHORTER than the addon's own `height` is silently clamped back up. **The fix for a half-empty panel is more content, never a smaller box, and the fix for an OVERFULL panel is less content, never a taller box**, so the picture stays the panel a player actually gets on install: a row too many pushes the outcome line off the bottom and clips its second line, which in a Browse thumbnail reads as a broken addon. The scale comes from `MIN_DEVICE_WIDTH`, the site's own card slot, and it is VERIFIED against the capture rather than predicted from it, because a frame sized by its content lays out differently at another scale factor. **A capture has to clear that slot by `SLOT_MARGIN` before the smaller scale is accepted**, because the choice is discrete over a continuous measurement and without a margin two pixels decide the resolution: `trailmark` is a 300px frame, so it crops to 348 CSS px and 2x falls four short, while the same tree measured 350 under another rasteriser, where 2x lands on 700 exactly. It captured at 3x and then at 2x, half the pixels, with a quest row ellipsised that had fitted. 16 absorbs the 2 to 12 pixels measured between CoreText and FreeType over the same fonts and between runs of one machine; past that a width change is content, and changing scale for content is the rule working. Growing for width and shrinking for the 512 kB cap are two separate passes in that order, because run together they oscillate.
- **A preview may be a SHEET of several scenarios, and every panel is its own iframe.** An addon whose LAYOUT is a setting has two pictures worth taking and a Browse row with space for one, so several scenarios may carry `preview: true`, drawn left to right in array order with a `caption` under each. Mounting one addon twice in ONE document breaks three ways at once, which is what the iframes are for: two elements carrying `#woc-addons`, two registrations of the same keybind fighting over it, and one fqid meaning one storage namespace and one bus identity. Same-origin panes cost nothing and compose the readiness contract for free, since each reaches its own `data-stage="ready"`. Captions are drawn in the PAGE rather than composited afterwards, because sharp renders text through librsvg against installed system fonts and Cinzel is not one. **The margin is applied once, per pane, and the sheet crops exactly**: each pane leaves 24px around its own frames for the panel shadow, and a second margin at the outer edge puts the panels adrift. The sheet's `padding-bottom` does need stating separately, because the caption is the last thing in the picture. **A SHEET HAS A WIDTH BUDGET OF 1440 AND NOTHING CHECKS IT.** The capture runs in a 1440px viewport (`VIEWPORT` in `tools/shots.mjs`), each pane carries its own 24px on each side and panes sit 16px apart, so a scenario has to satisfy `panes * (box + 48) + (panes - 1) * 16 <= 1440`. Over it, the last pane is cropped at the right edge: nothing fails, nothing warns, and the alt text then describes a picture missing what it names. Only looking at the capture finds it.
- **`pnpm shots` refuses to guess three things, and the third is the one worth defending.** WHICH scenario is an explicit `preview: true`, because position deciding is invisible and `idle` is first in more than one file. WHEN the panel is done is `data-stage="ready"`, written by the page once the scenario's own `run` has resolved, because scenarios take genuinely different times and a sleep long enough for the slowest still fails as a plausible photograph of a half-drawn panel. And WHAT THE PICTURE SHOWS is never generated: `alt` is written on the scenario, beside the fixture that produces it, and copied into the manifest verbatim. It is the sentence a screen reader reads instead of the image, and inventing one is worse than having none, which is why `pnpm validate` only checks a preview somebody declared.
- **The stage shows the game's DEFAULT theme and can only ever show that.** The game has a theme picker, and `src/ui/theme.ts` rewrites a fixed subset of these tokens on `documentElement` at run time, in JavaScript. Those alternate values are in no stylesheet and cannot be read from one.

## Dependencies

Ask before adding one, and install the **latest** version. Do not pick an older major to dodge a peer conflict; move the related stack forward together (vite, vite-plugin-monkey, and vitest majors track each other).

In use: `playwright` (headless capture for `pnpm shots`, dev only; needs `pnpm exec playwright install chromium` once), `sharp` (the derivatives `pnpm site` builds and the crop `pnpm shots` writes, dev only), `zod` (schemas, host and tools only), `semver` (gameVersion ranges), `comlink` (bridge RPC), `preact` (manager UI only, never exposed to addons), `interactjs` (frame drag and resize), `happy-dom` (DOM tests), `esbuild` (the runtime and stage bundles, called directly from `loader/build-runtime.mjs` and `loader/build-stage.mjs` rather than through vite), `markdown-it` and `shiki` (the site's docs rendering and its code highlighting, dev only), `vite-plugin-monkey` (userscript build), `@types/node` (types only, for `tools/*.ts`), `git-cliff` (changelog generation, dev only, pinned EXACTLY rather than by range so it matches the version `release.yml` pins the action to).

The preact JSX transform is configured in **three** places and they have to agree: `jsx`/`jsxImportSource` in `tsconfig.json`, `jsx`/`jsxImportSource` in `loader/build-runtime.mjs`, and `oxc.jsx` in `vitest.config.ts`. Vitest 4 transforms with oxc, so an `esbuild` key there is accepted and then silently ignored, which shows up as JSX compiling against react.

## Testing

Pure modules in `shared/` and `runtime/disposal.ts` are unit tested. DOM-touching modules opt into happy-dom per file:

```ts
// @vitest-environment happy-dom
```

`addons/dev-harness` is the other half of the suite: an ordinary addon, fetched over the marketplace path and evaluated with only the published `woc` object in scope. `addons/dev-harness/main.test.ts` runs it through the real loader and requires every check to pass, which catches the two failures a unit suite cannot see: a surface that was never wired to the object an addon is handed, and an addon written against an API that has since moved.

**An addon's screenshot lives in the addon's directory too, declared by its own manifest.** `preview` is `{ file, alt }` on `addon.json`, the file is a PNG beside `main.js`, and THREE consumers read that one declaration: the manager draws a lazy thumbnail on every Browse row and the full picture on the install confirmation, the site's catalog and landing pages build their own AVIF and WebP from it, and the README links the PNG directly so GitHub renders it. One file, committed once.

Three things about it are not obvious. The manager loads it as an ordinary cross-origin `<img>` from the page, which works because **the game sets no Content-Security-Policy** and its own source says one is deferred rather than declined, so `manager/preview.tsx` hides the slot on a failed load the way `ui/kit/bar.ts` hides an icon that 404s; if a policy lands, the fallback is to fetch it in the host, where `raw.githubusercontent.com` is already in the `@connect` list. The URL is built in the RUNTIME rather than carried over the bridge, which is not an inconsistency with update rows: those are computed in the host because comparing versions needs semver, and a marketplace URL needs nothing banned. And previews are deliberately left out of the site's undersize report, because an addon's preview is nearly always a picture of its own fixed-size panel, which cannot be captured wider without zooming the game.

`pnpm validate` checks the file exists, is a PNG by signature as well as by name, and is under half a megabyte. That ceiling is the one asset budget here a player pays at a moment they did not choose, since the manager loads it inside the running game.

**An addon's suite lives in the addon's directory, as `main.test.ts`.** `tests/` is about the LOADER; a suite about one addon belongs beside the file it runs, and it travels with the directory a third-party marketplace would copy. Three things make that true rather than merely tidy: `vitest.config.ts` includes `addons/*/*.test.ts`, `tsconfig.json` includes the same glob so `tsc --noEmit` still typechecks it, and the `tests/**` block in `biome.json` names the glob too and sits after the `addons/**` one so the test relaxations win. `tests/addons-suites.test.ts` fails if any addon directory has no suite, because the failure it catches is a green run with one fewer file in it rather than a red one.

Start from `tests/fakes/addon.ts`. `mountAddon` parses the REAL `addon.json` through the schema CI uses, seeds settings BEFORE evaluating (the loader hydrates and then runs the body, and an addon reads `woc.settings` while building its first frame), and returns one `dispose` covering both the addon and the shared services. Everything an addon suite adds on top is the fake world that addon needs.

**Anything that touches the game's wire or its live state is verified by hand against a running PBE client before it is called done.** Mocking those would test the mock, and the failures they produce are silent: a field read at the wrong nesting level, or under the wire's name instead of the entity's, simply never matches and never complains. Build a throwaway userscript that imports the real modules, run it against a live session, and turn what it observed into a fixture. That is how the bootstrap handshake, the `__game` probe, the socket hook, and the `world.on` signatures were each checked.

Write tests that fail on regression, not tests that restate the implementation. When fixing a bug, add the failing test first.

## Style

The mechanical rules are in [STYLE.md](STYLE.md), which is the one to read before writing code. What follows is the part that is this project's taste rather than the linter's.

- TypeScript strict, ESM, explicit `.ts` extensions on relative imports.
- Private declarations come first in a file, the exported surface last. `useExportsLast` enforces it.
- Module size is a design constraint, not a cleanup task: 50 lines per function body and 300 per file. A factory that outgrows 50 lines is usually holding two concerns; split it while writing it rather than when the linter says so.
- Markdown is not hard-wrapped. One line per paragraph or bullet, however long.
- No em dashes, en dashes, or emoji anywhere: code, comments, docs, or commits. Use commas, colons, parentheses, or "to" for ranges.
- Commit titles are a capitalized imperative verb phrase, with no type prefix, no scope parentheses, and no colon: `Scaffold the addon loader workspace`, not `chore(loader): scaffold workspace`. Every commit carries a body explaining what changed and why.
- Comments explain intent and non-obvious constraints, not what the code says. No separator comments; if a file needs sections, split it.

## Development target

Develop against `https://pbe.worldofclaudecraft.com` or `pbe2`, where game drift shows up first, so the per-host probe gets exercised by real change rather than staying speculative.

**"Ahead" is the wrong model, and a version string is not the answer.** The two channels DIVERGE IN BOTH DIRECTIONS, and the version they report says nothing useful about which content each carries. Measured 2026-08-04, when live reported v0.34.0 and pbe reported v0.33.0: the hunter skill manifest carried 25 ids on live and 32 on pbe, with EIGHT live-only (`wyvern_sting`, `multi_shot`, `deterrence` among them) and FIFTEEN pbe-only. So the channel reporting the OLDER version was simultaneously missing content live had and serving content live did not. Neither channel is a superset, and a version comparison cannot tell you which way a given id falls.

**And the ORDER inverts too, which is the half that catches people who learned the first half.** Measured 2026-08-11: live was on v0.36.0 serving 822 item ids while both pbe channels sat on v0.35.0 under 700, so for that week the development channel was the stale one and `pnpm run stage` was showing an older game than a player's. **Measured again 2026-08-13, the gap had WIDENED rather than closed**: live v0.37.1 against v0.35.0 on both pbe channels, two releases. **Measured again 2026-08-16 it had widened again**: live v0.38.2 against the same v0.35.0 on both, three releases, so a stage session that week was showing a game two content releases behind whatever a player was in. **Measured again 2026-08-19 it had widened a fourth time**: live v0.39.0 against v0.35.0 on both pbe channels, now FOUR releases, and 0.39.0 is the one where that gap started costing something a reader can see, because it added a whole served art family (`/ui/auras/mapping.json`) that no pbe channel serves at all. **Measured again 2026-08-28 the gap had CLOSED rather than widened again**: live v0.40.1 against v0.40.0 on pbe2, one release, with pbe itself unreadable that day. Four consecutive readings said the gap was growing and the fifth said it was gone, which is the point of measuring rather than extrapolating: a trend across four cycles was worth exactly nothing as a prediction of the fifth. **An unreadable channel is its own reading and does not license a guess**: pbe answered nothing for a version string on 2026-08-28, so what it was serving that day is not recorded here, rather than being assumed to match pbe2. There is no standing relationship to remember. Read the channel you are about to generate from, every time.

What follows from it. Every by-hand generator that writes a COMMITTED artifact reads LIVE by default and takes `--host` to go elsewhere: `pnpm cues`, `pnpm icons`, `pnpm items`, `pnpm theme` and `pnpm shots`. The reason is not that live leads, because it does not; it is that a committed artifact describes what a PLAYER is running, and players are on live. `pnpm run stage` and `pnpm dev` keep pbe, because a person watching an addon react to an unshipped game wants the drift.

**A STAGE FIXTURE must use ids present on BOTH channels, and this is the rule that is easy to miss.** A preview is one committed file with nothing in it recording which channel it came from, so a fixture naming a live-only id photographs with art from live and without it from pbe, silently, and the alt text describing that row is then true or false depending on who ran the capture. Check an id on both before putting it in a fixture. Two committed artifacts have already carried the cost: a `theme.generated.css` generated from pbe carried a `--color-ruin-*` token family that existed in no game tag at the time, and a preview showed art live had not yet shipped, so for a stretch the committed picture showed players something their own game did not draw. A capture taken from the wrong channel is not a failure; it is a plausible picture of a game nobody is running. **That the ruin tokens are real now, having landed in 0.36.0, is the point rather than an acquittal:** a reading that is wrong when it is committed does not become right by being overtaken, and nothing in between would have told anybody.
